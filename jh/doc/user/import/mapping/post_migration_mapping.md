使用迁移后映射时，来自源实例的用户贡献和成员关系最初会分配给目标实例上的占位用户，而不是真实用户。

由于您可以推迟分配给真实用户，因此有时间审查导入结果，并将贡献重新分配给正确的用户。此过程可确保归属准确，同时让您掌控映射过程。

迁移后用户贡献和成员关系映射默认适用于以下来源的迁移：

- [使用直接转移的极狐GitLab](../../group/import/_index.md)
- [GitHub](../../project/import/github.md)
- [Bitbucket Server](../bitbucket_server.md)
- [Gitea](../gitea.md)

当您将项目导入到[个人命名空间](../../namespace/_index.md#types-of-namespaces)时，不支持用户贡献映射和成员关系映射，所有贡献都会分配给个人命名空间所有者。这些贡献无法重新分配。

<a id="prerequisites"></a>

## 先决条件

- 根据[用户限制](#placeholder-user-limits)规划用户数量。
- 如果导入到 JihuLab.com，请设置您的付费命名空间。
- 如果导入到 JihuLab.com 并使用 [JihuLab.com 群组的 SAML SSO](../../group/saml_sso/_index.md)，请确保所有用户都将其 SAML 身份关联到其 JihuLab.com 账号。

<a id="post-migration-mapping-workflow"></a>

## 迁移后映射工作流

使用迁移后映射时，极狐GitLab 会将您导入的任何成员关系和贡献映射到[占位用户](#placeholder-users)。即使目标实例上已存在使用相同电子邮件地址的用户，也会在目标实例上创建占位用户。在您重新分配目标实例上的贡献之前，所有贡献都与占位用户关联。

导入完成并审查结果后，您可以按如下方式更新映射：

- 将成员关系和贡献重新分配给目标实例上的现有用户。您可以为源实例和目标实例上电子邮件地址不同的用户映射成员关系和贡献。
- 在目标实例上创建新用户，并将成员关系和贡献重新分配给他们。

您也可以将某些贡献保留给占位用户，以保留历史背景信息。

当您将贡献重新分配给目标实例上的用户时，该用户可以：

- 接受重新分配。重新分配过程可能需要几分钟。在后续从同一源实例导入到目标实例上同一顶级群组或子群组时，贡献会自动映射到该用户。
- 拒绝重新分配。

<a id="enterprise-users"></a>

## 企业用户

如果您的顶级群组至少有一个[企业用户](../../enterprise_user/_index.md)，则只能将贡献重新分配给您组织中的企业用户。

这意味着您不会意外地重新分配给组织之外的用户。

<a id="deleted-users"></a>

## 已删除的用户

源实例上由现已删除的用户做出的贡献，会在目标实例上映射到[幽灵用户](../../../administration/internal_users.md)，但以下情况除外：

- 该贡献从未在源实例上正确地从已删除用户中分离。
- 从 Bitbucket Server 迁移。

<a id="placeholder-users"></a>

## 占位用户

使用贡献和成员关系映射时，您不会立即将贡献和成员关系分配给目标实例上的用户。相反，会为任何具有导入贡献或成员关系的活跃用户、非活跃用户或机器人用户创建一个占位用户。

贡献和成员关系最初都会分配给这些占位用户，并可在导入后重新分配给目标实例上的现有用户。

在重新分配之前，贡献与占位用户关联。占位成员关系不会显示在成员列表中。

占位用户不计入许可证限制。

<a id="exceptions"></a>

### 例外情况

在以下场景中不会创建占位用户：

- 您从 [Gitea](../gitea.md) 导入项目，且其中包含已删除用户的贡献。这些用户的贡献会映射到导入该项目的用户。
- 您已超出[占位用户限制](#placeholder-user-limits)。任何新用户的贡献都会映射到导入用户。

<a id="placeholder-user-attributes"></a>

### 占位用户属性

占位用户与普通用户不同，不能：

- 登录。
- 执行任何操作。例如，运行流水线。
- 在议题和合并请求中作为指派人或审核人出现在建议中。
- 成为项目和群组的成员。

为了保持与源实例上用户的关联，占位用户具有：

- 唯一标识符（`source_user_id`），导入过程使用它来确定是否需要新的占位用户。
- 源主机名或域名（`source_hostname`）。
- 源用户的名称（`source_name`），以帮助重新分配贡献。
- 源用户的用户名（`source_username`），以便群组所有者在重新分配贡献时使用。
- 导入类型（`import_type`），用于区分是哪个导入器创建了该占位用户。
- 源用户创建时间的时间戳（`created_at`，本地时间），用于迁移跟踪（在极狐GitLab 17.10 中[引入](https://gitlab.com/gitlab-org/gitlab/-/issues/507297)）。

为保留历史背景信息，占位用户的名称和用户名派生自源用户的名称和用户名：

- 占位用户的名称是 `Placeholder <source user name>`。
- 占位用户的用户名是 `%{source_username}_placeholder_user_%{incremental_number}`。

<a id="view-placeholder-users"></a>

### 查看占位用户

先决条件：

- 您必须具有该群组的所有者角色。

在导入群组或项目时，会在目标实例上创建占位用户。要查看导入到顶级群组及其子群组期间创建的占位用户：

1. 在顶部栏中，选择**搜索或跳转到**，然后找到您的群组。该群组必须是顶级群组。
1. 在左侧边栏中，选择**管理** > **成员**。
1. 选择**占位用户**标签页。

### 筛选占位用户

先决条件：

在导入群组或项目时，会在目标实例上创建占位用户。要筛选整个实例在导入期间创建的占位用户：

<a id="creating-placeholder-users"></a>

### 创建占位用户

占位用户按导入来源和顶级群组创建：

- 如果您将同一项目两次导入到目标实例上的同一顶级群组，第二次导入会使用与第一次导入相同的占位用户。
- 如果您将同一项目导入两次，但导入到目标实例上的不同顶级群组，第二次导入会在该顶级群组下创建新的占位用户。

> [!note]
> 占位用户仅与顶级群组关联。
> 当您删除子群组或项目时，它们的占位用户
> 不再引用顶级群组中的任何贡献。
> 进行测试时，您应使用指定的顶级群组。
> 删除占位用户已在[议题 519391](https://gitlab.com/gitlab-org/gitlab/-/issues/519391)
> 和[议题 537340](https://gitlab.com/gitlab-org/gitlab/-/issues/537340)中提出。

当用户[接受重新分配](reassignment.md#accept-contribution-reassignment)后，后续从同一源实例导入到目标实例上同一顶级群组或子群组时，不会创建占位用户。相反，贡献会自动映射到该用户。

<a id="placeholder-user-deletion"></a>

### 删除占位用户

当您删除包含占位用户的顶级群组时，这些用户会自动安排移除。此过程可能需要一些时间才能完成。但是，如果占位用户还与其他项目或群组关联，它们会保留在系统中。

> [!note]
> 没有其他方式可以删除占位用户，但改进支持已在
> [议题 519391](https://gitlab.com/gitlab-org/gitlab/-/issues/519391) 和
> [议题 537340](https://gitlab.com/gitlab-org/gitlab/-/issues/537340)中提出。

<a id="placeholder-user-limits"></a>

### 占位用户限制

如果导入到 JihuLab.com，占位用户按目标实例上的顶级群组进行限制。限制因您的计划和席位数量而异。占位用户不计入许可证限制。

| JihuLab.com 计划          | 席位数 | 顶级群组的占位用户限制 |
|:-------------------------|:----------------|:------------------------------------------|
| 基础版和任何试用版       | 任意数量      | 200                                       |
| 专业版                  | < 100           | 500                                       |
| 专业版                  | 101-500         | 2000                                      |
| 专业版                  | 501 - 1000      | 4000                                      |
| 专业版                  | > 1000          | 6000                                      |
| 旗舰版和开源 | < 100           | 1000                                      |
| 旗舰版和开源 | 101-500         | 4000                                      |
| 旗舰版和开源 | 501 - 1000      | 6000                                      |
| 旗舰版和开源 | > 1000          | 8000                                      |

对于极狐GitLab 私有化部署，默认不适用占位用户限制。极狐GitLab 管理员可以在其实例上[设置占位用户限制](../../../administration/instance_limits.md#import-placeholder-user-limits)。

要查看您当前的占位用户使用情况和限制：

1. 在顶部栏中，选择**搜索或跳转到**，然后找到您的群组。该群组必须是顶级群组。
1. 选择**设置** > **用量配额**。
1. 选择**导入**标签页。

您无法提前确定需要多少占位用户。

达到占位用户限制时，所有贡献都会分配给一个名为 `Import User`的单一非功能性用户。分配给 `Import User`的贡献可能会被去重，并且某些贡献可能在导入期间不会创建。例如，如果来自合并请求审批人的多个审批分配给 `Import User`，则只会创建第一个审批，其他审批会被忽略。可能被去重的贡献包括：

- 审批规则
- Emoji 回应
- 议题指派人
- 成员关系
- 合并请求审批、指派人和审核人
- 推送、合并请求和部署访问级别

每次更改都会创建一条系统评论，系统评论不受占位用户限制的影响。

<a id="alternative-mapping-method"></a>

## 替代映射方法

迁移后映射的替代方法是在迁移期间进行映射。不建议使用此方法，并且发现的任何问题都不太可能被修复。

替代映射方法：

- 仅适用于迁移到极狐GitLab 私有化部署。
- 需要在迁移前进行一些准备，包括禁用适用的 `*_user_mapping` 功能标志。
- 适用于以下来源的迁移：
  - GitHub。
  - Bitbucket Server。
  - Gitea（适用于极狐GitLab 18.5 及更早版本）。

有关更多信息，请参阅每个导入器的替代映射方法文档。
