分阶段规划您的应用安全测试实施，以确保平稳过渡到更安全的开发实践。

本指南帮助您在组织中分阶段实施极狐GitLab 应用安全测试。通过从试点群组开始并逐步扩大覆盖范围，您可以在最大化安全收益的同时，最大限度地减少干扰。这种分阶段方法让您的团队在推广到所有项目之前，能够熟悉应用安全测试工具和工作流。

前提条件：

- 极狐GitLab 旗舰版。
- 熟悉极狐GitLab CI/CD 流水线。以下极狐GitLab 自学课程提供了很好的入门介绍：
  - [CI/CD 简介](https://university.gitlab.com/courses/introduction-to-cicd-s2)
  - [动手实验：CI 基础](https://university.gitlab.com/courses/hands-on-labs-ci-fundamentals)
- 了解您组织的安全要求和风险承受能力。

<a id="scope"></a>

## 范围

本指南涵盖如何规划和执行极狐GitLab 应用安全测试功能的分阶段实施，包括配置、漏洞管理和预防策略。它假设您希望逐步引入应用安全测试，以最大限度地减少对现有工作流的干扰，同时保护您的代码库。

<a id="phases"></a>

## 阶段

实施包括两个主要阶段：

1. **试点阶段**：为有限的项目集实施应用安全测试，以验证配置并培训团队。
1. **推广阶段**：利用在试点期间获得的知识，将应用安全测试扩展到所有目标项目。

<a id="pilot-phase"></a>

## 试点阶段

试点阶段允许您在更广泛的推广之前，以最小的风险应用应用安全测试。

在开始试点阶段之前，请考虑以下指导：

- 确定关键利益相关者，包括安全团队成员、开发者和项目经理。
- 选择能代表您代码库但对日常运营不关键的试点项目。
- 为开发者和安全团队成员安排培训课程。
- 记录当前的安全实践，以便衡量改进效果。

<a id="pilot-goals"></a>

### 试点目标

试点阶段帮助您实现几个关键目标：

- 在不拖慢开发速度的情况下实施应用安全测试

  在试点期间，应用安全测试结果在 UI 中对开发者可用，但不会阻塞合并请求。这种方法将风险降到试点范围之外的项目，同时收集关于您当前安全状况的宝贵数据。在推广阶段，您应使用[合并请求批准策略](#merge-request-approval-policy)，在合并请求中检测到漏洞时增加额外的批准门槛。
- 建立可扩展的检测方法

  以可扩展到更广泛推广范围内的所有项目的方式，在试点项目上实施应用安全测试。专注于那些能够良好扩展并可在不同项目间标准化的配置。
- 测试扫描时间

  在具有代表性的代码库和应用程序上测试扫描时间。
- 模拟漏洞修复工作流

  在开发者工作流中模拟检测、分类、分析和修复漏洞。验证工程师能否根据发现采取行动。
- 比较维护成本

  比较维护单一解决方案与集成多个端点解决方案的成本。它与 IDE、合并请求和流水线的集成度如何？

<a id="benefits-for-developers"></a>

#### 为开发者带来的好处

试点群组中的开发者将获得：

- 熟悉应用安全测试方法以及如何解读结果。
- 防止漏洞合并到默认分支的经验。
- 了解从默认分支检测到漏洞时开始的漏洞管理工作流。

<a id="benefits-for-security-management"></a>

#### 为安全管理带来的好处

参与试点的安全团队成员将获得：

- 在极狐GitLab 中进行漏洞跟踪和管理的经验。
- 用于建立安全基线和设定实际修复目标的数据。
- 在更广泛推广之前完善安全策略的见解。

<a id="pilot-plan"></a>

### 试点计划

周密的计划能确保有效的试点阶段。

<a id="roles-and-responsibilities"></a>

#### 角色和职责

明确谁负责：

- 配置应用安全测试
- 审查扫描结果
- 分类漏洞
- 管理修复
- 培训团队成员
- 衡量试点的成功

<a id="pilot-scope"></a>

### 试点范围

谨慎选择纳入试点阶段的项目。

在选择试点项目时考虑以下因素：

- 包含具有不同技术栈的项目，以测试应用安全测试的有效性。
- 选择有活跃开发的项目，以查看实时结果。
- 选择团队乐于学习新安全实践的项目。
- 避免从关键任务应用程序开始。

<a id="security-application-security-testing-order"></a>

### 安全应用安全测试顺序

按以下顺序引入安全应用安全测试。这平衡了价值和部署的难易程度。

- 依赖项扫描
- SAST
- 高级 SAST
- 流水线密钥检测
- 密钥推送保护
- 容器扫描
- DAST
- API 安全测试
- IaC 扫描
- 运维容器扫描

<a id="test-pilot-projects"></a>

## 测试试点项目

规划完成后，开始对您的试点项目实施应用安全测试。

<a id="set-up-testing-of-pilot-projects"></a>

### 设置试点项目测试

前提条件：

- 对于要启用应用安全测试的项目，您必须具有维护者角色。

对于范围内的每个项目：

1. 在顶部栏中，选择**搜索或跳转到**并找到您的项目。
1. 在左侧边栏中，选择**安全** > **安全配置**。
1. 展开**安全配置**。
1. 根据您项目的技术栈启用相应的应用安全测试。

有关更多详细信息，请参见[安全配置](security_configuration.md)。

<a id="for-developers"></a>

### 面向开发者

向开发者介绍能够提供安全发现可见性的工具。

<a id="pipeline-results"></a>

#### 流水线结果

开发者可以直接在流水线结果中查看安全发现。

前提条件：

- 对该项目具有开发者、维护者或所有者角色。

要查看流水线结果：

1. 在顶部栏中，选择**搜索或跳转到**并找到您的项目。
1. 在左侧边栏中，选择**构建** > **流水线**。
1. 选择要审查的流水线。
1. 在流水线详情中，选择**安全**选项卡以查看检测到的漏洞。

有关更多详细信息，请参见
[查看流水线中的安全扫描结果](security_scanning_results.md)。

<a id="merge-request-security-widget"></a>

#### 合并请求安全小组件

安全小组件提供了对合并请求流水线中检测到的漏洞的可见性。

前提条件：

- 对该项目具有开发者、维护者或所有者角色。

要查看安全小组件：

1. 打开一个合并请求。
1. 审查安全小组件以查看检测到的漏洞。
1. 选择**展开**以查看详细发现。

有关更多详细信息，请参见[查看合并请求中的安全扫描结果](security_scanning_results.md)。

<a id="vulnerability-management-workflow"></a>

## 漏洞管理工作流

为处理检测到的漏洞建立一个结构化的工作流。

漏洞管理工作流包含四个关键阶段：

1. **检测**：通过流水线中的自动化应用安全测试发现漏洞。
1. **分类**：评估检测到的漏洞的严重性和影响。
1. **分析**：调查根本原因并确定修复的最佳方法。
1. **修复**：实施修复以解决漏洞。

<a id="efficient-triage"></a>

### 高效分类

极狐GitLab 提供了几个功能来简化漏洞分类：

- 漏洞过滤器，用于首先关注高影响的问题。
- 严重性和置信度评级，用于确定工作的优先级。
- 漏洞跟踪，用于保持对未解决问题的可见性。
- 风险评估数据。

有关更多详细信息，请参见[分类](../triage/_index.md)。

分类应包括与安全利益相关者定期审查漏洞报告。

<a id="efficient-remediation"></a>

### 高效修复

使用以下极狐GitLab 功能简化修复流程：

- 针对特定漏洞类型的自动化修复建议。
- 直接从漏洞详情创建合并请求。
- 漏洞历史跟踪，用于监控进度。
- 自动解决不再被检测到的漏洞。

有关更多详细信息，请参见[修复](../remediate/_index.md)。

<a id="integrate-with-ticketing-systems"></a>

#### 与工单系统集成

您可以使用极狐GitLab 议题来跟踪修复漏洞所需的工作。或者，如果 Jira 是您主要的工单系统，您也可以使用 Jira 议题。

有关更多详细信息，请参见
[将漏洞关联到极狐GitLab 和 Jira 议题](../vulnerabilities/_index.md#linking-a-vulnerability-to-gitlab-and-jira-issues)。

<a id="vulnerability-prevention"></a>

## 漏洞预防

实施功能，从源头防止漏洞被引入。

<a id="merge-request-approval-policy"></a>

### 合并请求批准策略

使用合并请求批准策略，当合并请求中漏洞的数量和严重性超过特定阈值时，增加额外的审批要求。这允许应用安全团队的成员进行额外审查，提供更高层次的审查力度。

前提条件：

- 对于群组具有所有者角色，或具有 `manage_security_policy_link` 权限的自定义角色。

配置批准策略以要求安全审查：

1. 在顶部栏中，选择**搜索或跳转到**并找到您的群组。
1. 在左侧边栏中，选择**安全** > **策略**。
1. 选择**新建策略**。
1. 在**合并请求批准策略**窗格中，选择**选择策略**。
1. 添加一个要求安全团队成员批准的合并请求批准策略。

有关更多详细信息，请参见
[合并请求中的安全批准](../policies/merge_request_approval_policies.md)。

<a id="rollout-phase"></a>

## 推广阶段

在试点成功后，将应用安全测试扩展到所有目标项目。

在开始推广阶段之前，请考虑以下事项：

- 评估试点阶段的结果。
- 记录经验教训和最佳实践。
- 根据试点经验准备培训材料。
- 根据试点反馈更新实施计划。

<a id="define-access-to-team-members"></a>

### 为团队成员定义访问权限

应用安全测试任务需要特定的角色或权限。对于参与推广阶段的每个人，根据他们将执行的任务定义其访问权限。

- 具有开发者角色的用户可以查看其项目和合并请求中的漏洞。
- 具有维护者角色的用户可以为项目配置安全设置。
- 被分配了具有 `admin_vulnerability` 权限的自定义角色的用户可以管理和分类漏洞。
- 被分配了具有 `manage_security_policy_link` 权限的自定义角色的用户可以对群组和项目执行策略。

有关更多详细信息，请参见
[角色和权限](../../permissions.md#group-application-security)。

<a id="rollout-goals"></a>

### 推广目标

推广阶段旨在利用在试点中获得的知识和经验，在范围内的所有项目上实施应用安全测试。

<a id="rollout-plan"></a>

### 推广计划

审查并更新在试点期间建立的角色和职责。相同的团队结构应该适用于推广，但随着范围的扩大，您可能需要增加更多团队成员。

<a id="implement-application-security-testing-at-scale"></a>

## 规模化实施应用安全测试

使用策略功能来高效地扩展您的安全实施。

<a id="use-policy-inheritance"></a>

### 使用策略继承

利用策略继承来最大化效率，同时最大限度地减少需要管理的策略数量。

考虑以下场景：您有一个名为 Finance 的顶级群组，它包含子群组 A、B 和 C。您希望对 Finance 群组中的所有项目运行依赖项扫描和密钥检测。对于每个子群组，您希望运行不同的应用安全测试工具集。

为实现此目标，您可以为 Finance 群组定义 3 个策略：

- 策略 1:
  - 包含依赖项扫描和密钥检测。
  - 应用于 Finance 群组、其所有子群组及其项目。
- 策略 2:
  - 包含 DAST 和 API 安全测试。
  - 限定范围仅应用于子群组 A 和 B。
- 策略 3:
  - 包含 SAST。
  - 限定范围仅应用于子群组 C。

只需维护一组策略，但仍然提供了满足不同项目需求的灵活性。

有关更多详细信息，请参见[执行](../policies/enforcement/_index.md#enforcement)。

<a id="configure-scan-execution-policies"></a>

### 配置扫描执行策略

通过使用扫描执行策略，在多个项目上实施一致的应用安全测试。

前提条件：

- 对于要启用应用安全测试的群组，您必须具有所有者角色，或具有 `manage_security_policy_link` 权限的自定义角色。

1. 在顶部栏中，选择**搜索或跳转到**并找到您的项目或群组。
1. 在左侧边栏中，选择**安全** > **策略**。
1. 基于试点阶段使用的应用安全测试配置，创建扫描执行策略。

有关更多详细信息，请参见[安全策略](../policies/_index.md)。

<a id="scale-gradually"></a>

### 逐步推广

逐步扩大推广范围，首先从试点项目开始，然后递增地覆盖所有目标项目。将策略应用于所有群组和项目时，请告知所有项目利益相关者，因为这可能会影响流水线和合并请求工作流的变更。例如，通知利益相关者。

分阶段实施您的安全策略：

1. 首先将策略应用于试点阶段的项目。
1. 监控是否有任何问题或中断。
1. 逐步扩大策略的范围以包含更多项目。
1. 持续进行，直到所有目标项目都覆盖。

有关更多详细信息，请参见[策略设计指南](../policies/enforcement/_index.md#policy-design-guidelines)。
