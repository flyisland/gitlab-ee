分阶段规划应用安全测试的实施，以确保平稳过渡到更安全的开发实践。

本指南帮助您分阶段在整个组织中实施极狐GitLab 应用安全测试。从试点群组开始并逐步扩大覆盖范围，您可以在最大化安全收益的同时将干扰降到最低。分阶段方法让您的团队在扩展到所有项目之前，先熟悉应用安全测试工具和工作流。

先决条件：

- 极狐GitLab 旗舰版。
- 熟悉极狐GitLab CI/CD 流水线。
- 了解您组织的安全要求和风险容忍度。

<a id="scope"></a>

## 范围

本指南介绍如何规划和执行极狐GitLab 应用安全测试功能的分阶段实施，包括配置、漏洞管理和预防策略。本指南假设您希望逐步引入应用安全测试，以在保护代码库的同时尽量减少对现有工作流的干扰。

<a id="phases"></a>

## 阶段

实施包含两个主要阶段：

1. **试点阶段**：为有限的一组项目实施应用安全测试，以验证配置并培训团队。
1. **推广阶段**：利用试点期间获得的知识，将应用安全测试扩展到所有目标项目。

<a id="pilot-phase"></a>

## 试点阶段

试点阶段让您可以在更大范围推广之前，以最低风险开展应用安全测试。

在开始试点阶段之前，请考虑以下指导：

- 确定关键利益相关者，包括安全团队成员、开发者和项目经理。
- 选择能代表您代码库、但对日常运营并非至关重要的试点项目。
- 为开发者和安全团队成员安排培训课程。
- 记录当前的安全实践，以便衡量改进情况。

<a id="pilot-goals"></a>

### 试点目标

试点阶段帮助您实现几个关键目标：

- 在不拖慢开发的情况下实施应用安全测试

  在试点期间，开发者可以在 UI 中查看应用安全测试结果，而不会阻塞合并请求。这种方法将试点范围之外项目的风险降到最低，同时收集有关您当前安全状况的宝贵数据。在推广阶段，您应使用[合并请求审批策略](#merge-request-approval-policy)，在合并请求中检测到漏洞时增加一道额外的审批关卡。
- 建立可扩展的检测方法

  在试点项目上实施应用安全测试时，要确保其方式可以扩展到更广泛推广范围内的所有项目。重点关注可良好扩展并能在各项目间标准化的配置。
- 测试扫描时间

  在具有代表性的代码库和应用程序上测试扫描时间。
- 模拟漏洞修复工作流

  在开发者工作流中模拟检测、分类、分析和修复漏洞的过程。验证工程师能否根据发现结果采取行动。
- 比较维护成本

  比较单一解决方案与集成多个端点解决方案的维护成本。它与 IDE、合并请求和流水线的集成效果如何？

<a id="benefits-for-developers"></a>

#### 对开发者的好处

试点群组中的开发者将获得：

- 熟悉应用安全测试方法以及如何解读结果。
- 积累防止漏洞被合并到默认分支的经验。
- 了解从默认分支中检测到漏洞时开始的漏洞管理工作流。

<a id="benefits-for-security-management"></a>

#### 对安全管理的好处

参与试点的安全团队成员将获得：

- 在极狐GitLab 中进行漏洞跟踪和管理的经验。
- 用于建立安全基线和设定切合实际的修复目标的数据。
- 用于在更广泛推广之前完善安全策略的洞察。

<a id="pilot-plan"></a>

### 试点计划

妥善规划可确保试点阶段有效进行。

<a id="roles-and-responsibilities"></a>

#### 角色和职责

定义谁负责：

- 配置应用安全测试
- 审阅扫描结果
- 分类漏洞
- 管理修复
- 培训团队成员
- 衡量试点是否成功

<a id="pilot-scope"></a>

### 试点范围

仔细选择要纳入试点阶段的项目。

选择试点项目时，请考虑以下因素：

- 纳入具有不同技术栈的项目，以测试应用安全测试的有效性。
- 选择正在积极开发的项目，以便看到实时结果。
- 选择团队愿意学习新安全实践的项目。
- 避免从关键业务应用程序开始。

<a id="application-security-testing-order"></a>

### 应用安全测试顺序

按以下顺序引入应用安全测试。这样可以在价值与部署难易度之间取得平衡。

- 依赖扫描
- SAST
- 高级 SAST
- 流水线密钥检测
- 密钥推送保护
- 容器扫描
- DAST
- API 安全测试
- IaC 扫描
- 运维容器扫描

<a id="test-pilot-projects"></a>

## 测试试点项目

规划完成后，开始对您的试点项目实施应用安全测试。

<a id="set-up-testing-of-pilot-projects"></a>

### 设置试点项目的测试

先决条件：

- 您必须对要启用应用安全测试的项目具有维护者角色。

对于范围内的每个项目：

1. 在顶部栏中，选择**搜索或跳转到**，然后找到您的项目。
1. 在左侧边栏中，选择**安全** > **安全配置**。
1. 展开**安全配置**。
1. 根据项目的技术栈启用相应的应用安全测试。

更多详情，请参见[安全配置](security_configuration.md)。

<a id="for-developers"></a>

### 面向开发者

向开发者介绍可让他们了解安全发现结果的工具。

<a id="pipeline-results"></a>

#### 流水线结果

开发者可以直接在流水线结果中查看安全发现结果。

先决条件：

- 对项目具有开发者、维护者或所有者角色。

查看流水线结果：

1. 在顶部栏中，选择**搜索或跳转到**，然后找到您的项目。
1. 在左侧边栏中，选择**构建** > **流水线**。
1. 选择要审阅的流水线。
1. 在流水线详情中，选择**安全**标签页以查看检测到的漏洞。

更多详情，请参见[在流水线中查看安全扫描结果](security_scanning_results.md)。

<a id="merge-request-reports"></a>

#### 合并请求报告

有关合并请求中的安全扫描结果，请参见[合并请求报告](../../project/merge_requests/reports.md)。

<a id="vs-code-integration"></a>

#### VS Code 集成

开发者可以直接在其 IDE 中查看安全发现结果。

先决条件：

在 VS Code 中查看安全发现结果：

<a id="vulnerability-management-workflow"></a>

## 漏洞管理工作流

建立处理检测到的漏洞的结构化工作流。

漏洞管理工作流包含四个关键阶段：

1. **检测**：通过流水线中的自动化应用安全测试发现漏洞。
1. **排查**：评估检测到的漏洞的严重程度和影响。
1. **分析**：调查根本原因并确定最佳修复方法。
1. **修复**：实施修复以解决漏洞。

<a id="efficient-triage"></a>

### 高效分类

极狐GitLab 提供多项功能来简化漏洞排查：

- 漏洞筛选器，可优先关注影响较大的问题。
- 严重程度和置信度评级，用于确定工作优先级。
- 漏洞跟踪，用于持续了解未解决的问题。
- 风险评估数据。

更多详情，请参见[分类](../triage/_index.md)。

分类应包括与安全利益相关者定期审阅漏洞报告。

<a id="efficient-remediation"></a>

### 高效修复

使用以下极狐GitLab 功能简化修复流程：

- 针对某些漏洞类型的自动修复建议。
- 直接从漏洞详情创建合并请求。
- 漏洞历史记录跟踪，用于监控进度。
- 自动解决不再检测到的漏洞。

更多详情，请参见[修复](../remediate/_index.md)。

<a id="integrate-with-ticketing-systems"></a>

#### 与工单系统集成

您可以使用极狐GitLab 议题来跟踪漏洞所需的修复工作。或者，如果 Jira 是您的主要工单系统，您也可以使用 Jira 议题。

更多详情，请参见[将漏洞链接到极狐GitLab 和 Jira 议题](../vulnerabilities/_index.md#linking-a-vulnerability-to-gitlab-and-jira-issues)。

<a id="vulnerability-prevention"></a>

## 漏洞预防

实施相关功能，从一开始就防止引入漏洞。

<a id="merge-request-approval-policy"></a>

### 合并请求审批策略

如果合并请求中的漏洞数量和严重程度超过特定阈值，可使用合并请求审批策略增加额外的审批要求。这样可以让应用安全团队的成员进行额外审阅，提供额外一层审查。

先决条件：

- 对群组具有所有者角色，或具有 `manage_security_policy_link` 权限的自定义角色。

配置审批策略以要求安全审阅：

1. 在顶部栏中，选择**搜索或跳转到**，然后找到您的群组。
1. 在左侧边栏中，选择**安全** > **策略**。
1. 选择**新建策略**。
1. 在**合并请求审批策略**窗格中，选择**选择策略**。
1. 添加要求安全团队成员批准的合并请求审批策略。

更多详情，请参见[合并请求中的安全审批](../policies/merge_request_approval_policies.md)。

<a id="rollout-phase"></a>

## 推广阶段

试点成功后，将应用安全测试扩展到所有目标项目。

在开始推广阶段之前，请考虑以下事项：

- 评估试点阶段的结果。
- 记录经验教训和最佳实践。
- 根据试点经验准备培训材料。
- 根据试点反馈更新实施计划。

<a id="define-access-to-team-members"></a>

### 定义团队成员的访问权限

应用安全测试任务需要特定的角色或权限。对于参与推广阶段的每个人，根据他们将执行的任务定义其访问权限。

- 具有开发者角色的用户可以查看其项目和合并请求上的漏洞。
- 具有维护者角色的用户可以为项目配置安全配置。
- 被分配具有 `admin_vulnerability` 权限的自定义角色的用户可以管理和排查漏洞。
- 被分配具有 `manage_security_policy_link` 权限的自定义角色的用户可以在群组和项目上强制执行策略。

更多详情，请参见[角色和权限](../../permissions.md#group-application-security)。

<a id="rollout-goals"></a>

### 推广目标

推广阶段旨在利用试点期间获得的知识和经验，在范围内的所有项目中实施应用安全测试。

<a id="rollout-plan"></a>

### 推广计划

审阅并更新试点期间建立的角色和职责。相同的团队结构应适用于推广阶段，但随着范围扩大，您可能需要增加更多团队成员。

<a id="implement-application-security-testing-at-scale"></a>

## 大规模实施应用安全测试

使用策略功能高效扩展您的安全实施。

<a id="use-policy-inheritance"></a>

### 使用策略继承

使用策略继承来最大化效果，同时尽量减少需要管理的策略数量。

考虑以下场景：您有一个名为 Finance 的顶级群组，其中包含子群组 A、B 和 C。您希望在 Finance 群组的所有项目中运行依赖扫描和密钥检测。对于每个子群组，您希望运行不同的应用安全测试工具集。

为实现此目标，您可以为 Finance 群组定义 3 个策略：

- 策略 1：
  - 包含依赖扫描和密钥检测。
  - 应用于 Finance 群组、其所有子群组及其项目。
- 策略 2：
  - 包含 DAST 和 API 安全测试。
  - 仅限定于子群组 A 和 B。
- 策略 3：
  - 包含 SAST。
  - 仅限定于子群组 C。

只需维护一组策略，但仍具有满足不同项目需求的灵活性。

更多详情，请参见[强制执行](../policies/enforcement/_index.md#enforcement)。

<a id="configure-scan-execution-policies"></a>

### 配置扫描执行策略

通过使用扫描执行策略，在多个项目中实施一致的应用安全测试。

先决条件：

- 您必须对要启用应用安全测试的群组具有所有者角色，或具有 `manage_security_policy_link` 权限的自定义角色。

1. 在顶部栏中，选择**搜索或跳转到**，然后找到您的项目或群组。
1. 在左侧边栏中，选择**安全** > **策略**。
1. 根据试点阶段使用的应用安全测试配置创建扫描执行策略。

更多详情，请参见[安全策略](../policies/_index.md)。

<a id="scale-gradually"></a>

### 逐步扩展

逐步扩展推广范围，先推广到试点项目，再逐步推广到所有目标项目。在将策略应用于所有群组和项目时，请让所有项目利益相关者知晓，因为这可能会影响流水线和合并请求工作流中的变更。例如，通知利益相关者

分阶段实施您的安全策略：

1. 首先将策略应用于试点阶段的项目。
1. 监控是否有任何问题或干扰。
1. 逐步扩大策略范围以纳入更多项目。
1. 继续直到覆盖所有目标项目。

更多详情，请参见[策略设计指南](../policies/enforcement/_index.md#policy-design-guidelines)。
