<a id="policy-enforcement"></a>

## 策略执行

你可以为每个项目或群组创建一个新的安全策略，但在多个顶级群组之间重复相同的策略设置可能会耗时且带来合规挑战。创建策略之前，你应该明确该策略应该：

- 在特定项目或群组上强制执行。
- 在多个项目上强制执行。
- 在整个实例或顶级群组上强制执行。

你可以通过多种方式强制执行策略：

- 要在单个项目或群组中的所有项目中强制执行策略，请在该项目或群组中创建策略。
- 要在多个项目之间强制执行策略，请使用[安全策略项目](security_policy_projects.md)。安全策略项目是一种特殊类型的项目，你只能在里面添加策略，其他什么都不能加。要将安全策略项目中的策略强制执行到其他群组和项目上，请从目标群组或项目链接到该安全策略项目。
- 要在私有化部署实例上一起强制执行策略和合规框架，实例管理员可以使用[合规与安全策略管理群组](compliance_and_security_policy_groups.md)。

<a id="policy-design-guidelines"></a>

## 策略设计指南

在设计策略时：

- 最大化覆盖范围，同时最小化管理开销
- 确保职责分离

<a id="enforcement"></a>

### 强制执行

要强制执行策略以满足你的要求，请考虑以下因素：

- **继承**：默认情况下，策略会在其链接的组织单元以及它们的所有后代子群组和项目上强制执行。
- **范围**：要自定义策略强制执行，你可以定义策略的范围以满足需求。

<a id="inheritance"></a>

#### 继承

为了最大化策略覆盖范围，请将安全策略项目链接到符合目标的最高组织单元：群组、子群组或项目。策略会在其链接的组织单元以及它们的所有后代子群组和项目上强制执行。在最高点强制执行可最小化所需安全策略的数量，从而降低管理开销。

你可以利用策略继承来逐步推广策略。例如，在推广一个新策略时，你可以先在一个项目上强制执行，然后进行测试。如果测试通过，你可以将其从项目上移除，转而在一个群组上强制执行，并逐步向上层级，直到策略在所有适用的项目上强制执行。

在现有群组或子群组上强制执行的策略会自动应用于其下创建的任何新子群组和项目，前提是：

- 新子群组和项目包含在策略的范围定义中（例如，范围包含该群组中的所有项目）。
- 现有群组或子群组已链接到安全策略项目。

> [!note]
> JihuLab.com 用户可以对其顶级群组或跨子群组强制执行策略，但不能跨 JihuLab.com 顶级群组强制执行策略。私有化部署管理员可以跨实例中的多个顶级群组强制执行策略。

以下示例展示了两个群组及其结构：

- Alpha 群组包含两个子群组，每个子群组又包含多个项目。
- 安全与合规群组包含两个策略。

**Alpha** 群组（包含代码项目）

- **财务**（子群组）
  - 项目 A
  - 收款（子群组）
    - 项目 B
    - 项目 C
- **工程**（子群组）
  - 项目 K
  - 项目 L
  - 项目 M

**安全与合规** 群组（包含安全策略项目）

- 安全策略管理
- 安全策略管理 - 安全策略项目
  - SAST 策略
  - 密钥检测策略

假设尚未强制执行任何策略，请考虑以下示例：

- 如果“SAST”策略在 Alpha 群组强制执行，则该策略同时适用于 Alpha 的两个子群组（财务和工程）及其所有项目和子群组。如果密钥检测策略也在“收款”子群组强制执行，则两个策略都适用于项目 B 和 C。但是，只有“SAST”策略适用于项目 A。
- 如果“SAST”策略在“收款”子群组强制执行，则它只适用于项目 B 和 C。项目 A 没有策略适用。
- 如果密钥检测策略在项目 K 强制执行，则它只适用于项目 K。没有其他子群组或项目有策略适用。

<a id="scope"></a>

#### 范围

{{< history >}}

- 在极狐GitLab 16.7 中引入，通过一个名为 `security_policies_policy_scope` 的功能标志。默认启用。
- 在极狐GitLab 16.11 中 GA。功能标志 `security_policies_policy_scope` 已移除。

{{< /history >}}

你可以通过以下方式细化策略的范围：

- 合规框架：对具有选定合规框架的项目强制执行策略。
- 群组：
  - 群组中的所有项目，包括该群组的所有子群组及其项目。也可以选择排除特定项目。
  - 多个群组中的所有项目，包括所有群组的子群组及其项目。链接到同一个安全策略项目的任何群组都可以在策略中列出。也可以选择排除特定项目。
- 项目：包含或排除特定项目。只有链接到同一个安全策略项目的项目才能在策略中列出。

你可以在同一个策略中同时应用这些细化方式。但是，排除优先于包含。

<a id="separation-of-duties"></a>

## 职责分离

职责分离对于成功实施策略至关重要。
设计既能满足必要的合规和安全要求，又能支持开发工作流的策略。

实施职责分离时：

- 集中定义策略，并与开发团队协作，确保策略支持其工作流。
- 将策略修改权限限制为仅授权角色。

要在群组、子群组或项目上强制执行安全策略项目，你必须具备以下任一角色：

- 该群组、子群组或项目中的所有者角色。
- 该群组、子群组或项目中具有 `manage_security_policy_link` 权限的[自定义角色](../../../custom_roles/_index.md)。

所有者角色和具有 `manage_security_policy_link` 权限的自定义角色遵循跨群组、子群组和项目的标准层级规则：

| 组织单元 | 群组所有者或群组 `manage_security_policy_link` 权限 | 子群组所有者或子群组 `manage_security_policy_link` 权限 | 项目所有者或项目 `manage_security_policy_link` 权限 |

| 群组 | {{< yes >}} | {{< no >}}  | {{< no >}} |
| 子群组 | {{< yes >}} | {{< yes >}} | {{< no >}} |
| 项目 | {{< yes >}} | {{< yes >}} | {{< yes >}} |
