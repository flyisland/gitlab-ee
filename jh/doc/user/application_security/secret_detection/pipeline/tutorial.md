如果你的应用程序使用外部资源，通常需要使用密钥（如令牌或密钥）对应用程序进行认证。如果密钥被推送到远程代码仓库，任何有权访问该代码仓库的人都可以冒充你或你的应用程序。

流水线密钥检测使用 CI/CD 作业来检查极狐GitLab 项目中的密钥。在本教程中，你将创建一个项目，配置流水线密钥检测，并学习如何分析其结果：

1. [创建项目](#create-a-project)
1. [检查作业输出](#check-the-job-output)
1. [启用合并请求流水线](#enable-merge-request-pipelines)
1. [添加虚假密钥](#add-a-fake-secret)
1. [分类处置密钥](#triage-the-secret)
1. [修复泄漏](#remediate-a-leak)

<a id="before-you-begin"></a>

## 开始之前

在开始本教程之前，请确保你具备以下条件：

- 一个 JihuLab.com 账号。要充分利用流水线密钥检测的全部功能，如果拥有旗舰版账号，应使用旗舰版账号。
- 对 CI/CD 有一定的了解。

<a id="create-a-project"></a>

## 创建项目

首先，创建一个项目并启用密钥检测：

1. 在右上角，选择 **新建** ({{< icon name="plus" >}}) 和 **新建项目/代码仓**。
1. 选择 **创建空白项目**。
1. 输入项目详细信息：
   1. 输入名称和项目路径。
   1. 从 **项目部署目标（可选）** 下拉列表中，选择 **无部署计划**。
   1. 选中 **使用 README 初始化代码仓库** 复选框。这将为你之后向项目中添加内容提供一个位置。
   1. 选中 **启用密钥检测** 复选框。
1. 选择 **创建项目**。

将创建一个新项目，并使用 README 和 `.gitlab-ci.yml` 文件进行初始化。
CI/CD 配置中包含了 `Security/Secret-Detection.gitlab-ci.yml` 模板，该模板将在项目中启用流水线密钥检测。

<a id="check-the-job-output"></a>

## 检查作业输出

流水线密钥检测在一个名为 `secret_detection` 的 CI/CD 作业中运行。
扫描结果会被写入 CI/CD 作业日志。每次扫描还会生成一份综合报告作为作业产物。

要检查最近一次扫描的结果：

1. 在左侧边栏中，选择 **构建** > **作业**。
1. 选择最近的 `secret_detection` 作业。如果你尚未运行新流水线，应该只有一个作业。
1. 检查日志输出中的以下内容：
   - 有关扫描的信息，包括分析器版本和规则集。你的项目使用默认规则集，因为你自动启用了密钥检测。
   - 是否检测到任何密钥。你应该会看到 `未发现泄漏`。
1. 在 **作业产物** 下，要下载完整报告，请选择 **下载**。

<a id="enable-merge-request-pipelines"></a>

## 启用合并请求流水线

到目前为止，你已使用流水线密钥检测来扫描默认分支中的提交。但是，要在将合并请求中的提交合并到默认分支之前对其进行分析，你需要启用合并请求流水线。

为此：

1. 将以下行添加到你的 `.gitlab-ci.yml` 文件中：

   ```yaml
   variables:
     AST_ENABLE_MR_PIPELINES: "true"
   ```

1. 保存更改并将其提交到项目的 `主` 分支。

<a id="add-a-fake-secret"></a>

## 添加虚假密钥

接下来，我们通过在合并请求中“泄漏”一个虚假密钥来使作业输出复杂化：

1. 检出一个新分支：

   ```shell
   git checkout -b pipeline-sd-tutorial
   ```

1. 编辑项目 README 并添加以下行。请务必移除 `-`（短划线）前后的空格，以匹配个人访问令牌的确切格式：

   ```markdown
   # To make the example work, remove
   # the spaces before and after the dash:
   glpat - 12345678901234567890
   ```

1. 提交并推送你的更改，然后打开一个合并请求以将它们合并到默认分支。

   将自动运行合并请求流水线。
1. 等待流水线完成，然后检查作业日志。你应该会看到 `WRN 发现泄漏：1`。
1. 下载作业产物，并检查确保它包含以下信息：
   - 密钥类型。在此示例中，类型为 `"极狐GitLab 个人访问令牌"`。
   - 该密钥用途的描述，以及你可以采取的一些修复泄漏的步骤。
   - 泄漏的严重性。由于个人访问令牌可用于在 JihuLab.com 上冒充用户，因此此泄漏为 `严重`。
   - 密钥的原始文本。
   - 有关密钥位置的一些信息：

     ```json
     "file": "README.md",
     "line_start": 97,
     "line_end": 97,
     ```

     在此示例中，密钥位于文件 `README.md` 的第 97 行。

<a id="using-the-merge-request-security-widget"></a>

### 使用合并请求安全小部件

{{< details >}}

- Tier: 旗舰版

{{< /details >}}

在非默认分支上检测到的密钥被称为“发现”。
当发现被合并到默认分支时，它就变成了“漏洞”。

合并请求安全小部件会显示一系列发现，如果合并请求被合并，这些发现可能成为漏洞。

要查看小部件：

1. 选择你在上一步中创建的合并请求。
1. 找到以 **安全扫描** 开头的合并请求安全小部件。
1. 在小部件上，选择 **显示详细信息** ({{< icon name="chevron-down" >}})。
1. 查看显示的信息。你应该会看到 **密钥检测检测到 1 个新的潜在漏洞**。

要查看合并请求中所有发现的详细视图，请选择 **查看所有流水线发现**。

<a id="triage-the-secret"></a>

## 分类处置密钥

{{< details >}}

- Tier: 旗舰版

{{< /details >}}

在极狐GitLab 旗舰版上，作业输出还会写入：
- 流水线的 **安全** 选项卡。
- 如果发现变为漏洞，则写入漏洞报告。

为了演示如何通过 UI 分类处置密钥，我们来创建一个漏洞并在漏洞报告中更改其状态：

1. 合并你在上一步中创建的合并请求，然后等待流水线完成。

   虚假密钥被添加到 `主` 分支，导致该发现成为漏洞。
1. 在左侧边栏中，选择 **安全** > **漏洞报告**。
1. 选择漏洞的 **描述** 以查看：
   - 有关密钥类型的详细信息。
   - 修复指南。
   - 有关漏洞检测时间及位置的信息。
1. 选择 **编辑漏洞** > **更改状态**。
   1. 从 **状态** 下拉列表中，选择 **关闭为... 在测试中使用**。
   1. 添加一条注释，解释你为项目添加虚假密钥的原因。
   1. 选择 **更改状态**。

该漏洞不再出现在漏洞报告的首页。

<a id="remediate-a-leak"></a>

## 修复泄漏

如果你将密钥添加到远程代码仓库，该密钥就不再安全，必须尽快吊销。
即使密钥尚未合并到默认分支，你也应该将其吊销并替换。

修复泄漏的具体步骤取决于你组织的安全策略，但至少，你应该：

1. 吊销密钥。吊销密钥后，该密钥将不再有效，无法用于冒充合法活动。
1. 从代码仓库中删除密钥。

特定的修复指南会写入 `secret-detection` 作业日志，并可在漏洞报告详细信息页面上找到。
