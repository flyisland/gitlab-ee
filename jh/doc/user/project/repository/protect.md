代码仓库保护可防止对代码库进行未经授权的更改，同时维持开发工作流程。这些控制措施可帮助您解决常见的开发难题，包括：

- 对生产分支或受保护分支的意外提交。
- 提交历史中暴露的敏感数据。
- 绕过代码审查流程。
- 对关键文件的未经授权更改。
- 未经验证的提交作者身份。
- 不合规的代码进入主分支。

通过结合不同的保护方法，您可以创建协同工作的验证点，以强制执行组织标准。

更高级别的极狐GitLab 版本可访问额外的工具，以应用全面的安全扫描、执行合规性，并管理跨多个项目和群组的漏洞。在这些环境中，某些保护方法可能已被您的组织强制执行。有关这些高级安全工具的详细信息，请参见[保护您的应用程序](../../application_security/secure_your_application.md)。

<a id="protection-methods"></a>

保护方法

极狐GitLab 提供了多种保护方法，这些方法可协同工作以保护您的代码仓库。每种方法针对不同的安全需求，并可组合使用以实现全面保护。

| 保护方法 | 描述 | 何时使用 | 实例 | 群组 | 项目 |
|-------------------|-------------|-------------|----------|--------|----------|
| [受保护分支](branches/protected.md)                      | 控制分支权限，以确保代码稳定性和质量。                         | 控制谁可以推送和合并，防止意外删除，强制执行审查，或规范强制推送权限。 | {{< no >}}  | {{< yes >}} | {{< yes >}} |
| [合并请求审批](../merge_requests/approvals/_index.md) | 在更改合并前需要审批的审查流程。                                   | 要求代码审查，创建审批规则，或配置审批设置。                                      | {{< no >}}  | {{< yes >}} | {{< yes >}} |
| [推送规则](push_rules.md)                                      | 在提交、文件和标签进入仓库之前对其进行验证的预接收 Git 钩子。 | 评估提交内容，强制执行分支命名规则，防止标签删除，或要求签名提交。              | {{< yes >}} | {{< yes >}} | {{< yes >}} |
| [代码所有者](../codeowners/_index.md)                           | 定义代码库中特定文件和目录的专家。                 | 要求专家审批特定文件的更改，或标识代码维护的责任方。       | {{< no >}}  | {{< no >}}  | {{< yes >}} |
| [状态检查](../merge_requests/status_checks.md)              | 调用外部系统的 API 来验证合并请求状态。                              | 与第三方工作流工具集成，或根据外部质量要求进行验证。                      | {{< no >}}  | {{< no >}}  | {{< yes >}} |

<a id="branch-rules"></a>

分支规则

为了帮助您管理多种保护方法，极狐GitLab 为受保护分支、审批规则和状态检查提供了一个统一的[分支规则](branches/branch_rules.md)界面。使用项目设置中的**分支规则**页面，可以集中配置所有分支保护、查看各分支的保护状态以及管理复杂的保护组合。

> [!note]
> 对于群组保护，请在群组设置中配置受保护分支和推送规则。**分支规则**页面仅适用于项目。群组规则适用于群组内的所有项目，并与您创建的任何项目特定规则共同生效。

<a id="configure-your-protection-strategy"></a>

配置保护策略

根据工作流程和安全要求选择保护方法。以下是一些策略示例。

<a id="baseline-protection"></a>

基线保护

要在所有仓库中建立一致的安全标准：

- 为群组配置默认分支保护，以自动保护新项目。
- 设置受保护分支以控制谁可以推送和合并。
- 要求合并请求审批以强制执行同行审查。

<a id="comprehensive-protection"></a>

全面保护

通过分层保护来保护关键项目：

- 设置受保护分支和审批规则以控制谁可以推送和合并。
- 要求对包含敏感逻辑的文件进行代码所有者审批。
- 强制执行签名提交以验证作者身份。
- 添加状态检查以根据自动化测试进行验证。
- 将推送规则应用于群组以在所有项目中强制执行标准。

<a id="targeted-protection"></a>

针对性保护

要满足特定的安全要求：

- 当文件需要领域专家审查时，要求代码所有者审批。
- 强制执行推送规则以维护提交标准和内容限制。
- 当需要外部验证时，添加状态检查。
- 根据工作流程特定要求配置审批规则。

<a id="get-started"></a>

开始使用

先决条件：

- 您必须拥有项目的维护者或所有者角色，或群组的所有者角色。
- 确定需要保护的分支。
- 确定合规性和安全要求。

要配置和实施代码仓库保护：

1. 选择范围：
   - 对于群组规则，转到群组的 **设置** > **代码仓**。
   - 对于项目特定规则，转到项目的 **设置** > **代码仓** >
     **分支规则**。

2. 设置基线保护：
   - 为默认分支和其他关键分支创建受保护分支。
     - 在群组设置中：**设置** > **代码仓** > **受保护分支**。
     - 在项目设置中：**设置** > **代码仓** > **分支规则**。
   - 在 **设置** > **合并请求** >
     **合并请求审批** 中配置合并权限和审批要求。

3. 添加审查要求：
   - 在特定文件的 `CODEOWNERS` 文件中定义代码所有者。
   - 在 **设置** > **合并请求** 中配置审批规则。

4. 启用安全控制：
   - 配置推送规则：
     - 对于群组：**设置** > **代码仓** > **推送规则**。
     - 对于项目：**设置** > **代码仓** > **推送规则**。
   - 在 **设置** > **代码仓** > **推送规则** >
     **拒绝未签名的提交** 中启用签名提交。

5. 测试配置：
   - 创建一个测试合并请求。
   - 验证保护规则是否正常触发。
   - 根据结果调整设置。
