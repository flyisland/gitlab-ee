保护规则控制对分支的访问，并决定当多个规则适用于同一分支时会发生什么。它们帮助您为代码仓库分支实施适当的安全措施。这些规则涵盖：

- 权限级别、优先级和规则冲突。
- 跨多个匹配规则的强制推送权限。
- 代码所有者批准。
- 群组与项目之间的保护设置。

<a id="rule-behaviors"></a>

## 规则行为

当分支匹配到多个保护规则时，将应用以下行为：

- 群组规则应用于群组中的所有项目，且不能从项目设置中修改。
  更多信息，请参阅[跨群组和项目的规则](#rules-across-groups-and-projects)。
- 当分支匹配到多个规则时，最宽松的规则生效。但是，
  [代码所有者批准](#code-owner-approval) 使用最严格的规则。
- 精确的分支名称（如 `main`）不会覆盖通配符模式（如 `m*`）。

<a id="push-and-merge-permissions"></a>

## 推送和合并权限

{{< history >}}

- 分支推送权限在极狐GitLab 16.0 中[更改]，要求极狐GitLab 管理员也必须具有 **允许** 权限。

{{< /history >}}

当分支被保护时，默认行为会强制以下限制：

| 操作 | 谁可以执行 |
|:-------------------------|:--------------|
| 保护一个分支 | 具有维护者或所有者角色的用户。 |
| 推送到分支 | 具有 **允许** 权限的任何用户。(1) |
| 强制推送到分支 | 无任何人。 |
| 删除分支 | 无任何人。(2) |

1. 具有开发者角色的用户可以在群组中创建项目，但可能无法初始推送到[默认分支](default.md)。
2. 没有人可以通过 Git 命令删除受保护分支，但至少具有维护者角色的用户可以通过 UI 或 API [删除受保护分支](protected.md#delete-protected-branches)。

当您配置这些权限时，选择一个角色会授予拥有该角色以及所有更高角色的用户访问权限。例如：

- 选择 **维护者** 会授予维护者和所有者角色的用户访问权限。
- 选择 **开发者 + 维护者** 会授予开发者、维护者和所有者角色的用户访问权限。

此行为确保具有更高权限的用户保留具有较低权限用户可用的访问权限。

<a id="force-push-permissions"></a>

## 强制推送权限

强制推送权限遵循相同的最宽松规则适用的逻辑。例如，考虑以下包含通配符的规则：

| 分支名称模式 | 允许强制推送 |
|---------------------|------------------|
| `v1.x` | 是 |
| `v1.*` | 否 |
| `v*` | 否 |

名为 `v1.x` 的分支匹配所有三个分支名称模式：`v1.x`、`v1.*` 和 `v*`。因为最宽松的选项决定了行为，因此分支 `v1.x` 的结果权限为：

- **允许强制推送**：在三个设置中，`是` 是最宽松的，因此控制分支行为。尽管该分支还匹配 `v1.*` 和 `v*`（它们各自具有更严格的权限），任何可以推送到此分支的用户也可以强制推送。

<a id="code-owner-approval"></a>

## 代码所有者批准

{{< details >}}

- Tier: 专业版，旗舰版
- Offering: JihuLab.com，私有化部署

{{< /details >}}

与推送和合并权限以及强制推送权限不同，代码所有者批准使用最严格的规则。如果分支受到多个规则保护，当任一适用规则启用了**要求代码所有者批准**时，就需要代码所有者批准。更多信息，请参阅[要求代码所有者批准](protected.md#require-code-owner-approval)。

例如，考虑以下规则：

| 分支名称模式 | 代码所有者批准要求 |
|---------------------|------------------------------|
| `v1.x` | 是 |
| `v1.*` | 否 |
| `v*` | 否 |

名为 `v1.x` 的分支匹配所有三个分支名称模式：`v1.x`、`v1.*` 和 `v*`。由于至少有一个规则 (`v1.x`) 要求代码所有者批准，因此所有合并到此分支的合并请求都需要在合并之前获得代码所有者的批准。

<a id="rules-across-groups-and-projects"></a>

## 跨群组和项目的规则

分支保护规则可以在群组和项目中设置：

- 群组规则应用于群组中的所有项目，并且不能从项目设置中修改。
- 项目规则仅适用于设置它们的项目。

当群组和项目规则都匹配一个分支时，极狐GitLab 会一起评估所有匹配的规则：

- 对于大多数设置，最宽松的规则生效。
- 对于[代码所有者批准](#code-owner-approval)，最严格的规则生效。

您不能从项目设置中编辑或删除群组规则，但可以为同一分支添加项目规则。结合后的评估可能导致比仅群组规则更宽松的行为。

例如：

- 群组规则对 `main` 不允许强制推送。
- 项目维护者为 `main` 添加了一个允许强制推送的项目规则。
- 两个规则一起评估。最宽松的规则生效，因此在该项目的 `main` 分支上允许强制推送。

<a id="multiple-branch-rule-examples"></a>

## 多个分支规则示例

<a id="allowed-to-merge"></a>

### 允许合并

一个示例，说明精确的分支名称不会覆盖更宽松的通配符模式。

| 分支模式 | 允许合并 |
|----------------|---------------------------|
| `release-v1.0` | 无任何人 |
| `release*` | 维护者 |
| `*` | 开发者 + 维护者 |

- 分支 `release-v1.0` 匹配所有三个模式。最宽松的规则生效：
  - **允许合并**：开发者 + 维护者可以合并（来自 `*` 规则）。

<a id="allowed-to-push-and-merge"></a>

### 允许推送和合并

一个示例，说明多个分支规则如何应用于不同的分支名称。

| 分支模式 | 允许合并 | 允许推送和合并 |
|----------------|------------------------|---------------------------|
| `main` | 维护者 | 无任何人 |
| `m*` | 开发者 + 维护者 | 开发者 + 维护者 |
| `r*` | 无任何人 | 无任何人 |

- 分支 `main` 匹配两个模式（`main` 和 `m*`）。最宽松的规则生效：
  - **允许合并**：开发者 + 维护者可以合并（来自 `m*` 规则）。
  - **允许推送和合并**：开发者 + 维护者可以推送（来自 `m*` 规则）。
- 分支 `release-v1.0` 匹配一个模式：
  - **允许合并**：无任何人可以合并（来自 `r*` 规则）。
  - **允许推送和合并**：无任何人可以推送（来自 `r*` 规则）。

<a id="code-owner-requirements"></a>

### 代码所有者要求

代码所有者批准与其他分支保护设置不同。当多个规则匹配时，最严格的规则生效而非最宽松的。

| 分支模式 | 代码所有者批准要求 |
|----------------|------------------------------|
| `production` | 是 |
| `prod*` | 否 |
| `p*` | 是 |

- 分支 `production` 匹配所有三个模式。最严格的规则生效：
  - **代码所有者批准**：需要（来自 `production` 和 `p*` 规则）。
- 分支 `product-v1.0` 匹配两个模式（`prod*` 和 `p*`）。最严格的规则生效：
  - **代码所有者批准**：需要（来自 `p*` 规则）。

<a id="ensure-strict-protection"></a>

### 确保严格保护

为确保严格保护不被更宽松的模式覆盖，请将所有匹配模式配置为相同的严格设置。

| 分支模式 | 允许合并 | 允许推送和合并 |
|----------------|------------------|---------------------------|
| `production` | 维护者 | 无任何人 |
| `prod*` | 维护者 | 无任何人 |
| `p*` | 维护者 | 无任何人 |
| `*` | 维护者 | 无任何人 |

现在分支 `production` 具有严格的推送权限，因为所有匹配规则都指定**无任何人**可以推送。
