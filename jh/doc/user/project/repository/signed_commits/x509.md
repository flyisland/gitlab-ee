[X.509](https://en.wikipedia.org/wiki/X.509) 是一种由公共或私有公钥基础设施（PKI）颁发的公钥证书标准格式。个人 X.509 证书用于身份验证或签名目的，例如 S/MIME（安全/多用途互联网邮件扩展）。然而，Git 也支持使用 X.509 证书对提交和标签进行签名，方式类似于 [GPG（GnuPG，或 GNU Privacy Guard）](gpg.md)。主要区别在于极狐GitLab 判断开发者签名是否可信的方式：

- 对于 X.509，根证书颁发机构被添加到极狐GitLab 信任存储中。（信任存储是受信任安全证书的存储库。）结合签名中所需的任何中间证书，开发者的证书可以链回到受信任的根证书。
- 对于 GPG，开发者[将他们的 GPG 密钥](gpg.md#add-a-gpg-key-to-your-account)添加到他们的账户中。

极狐GitLab 使用自己的证书存储，因此定义了[信任链](https://www.ssl.com/article/what-is-a-certificate-authority-ca/)。要使提交或标签被极狐GitLab 验证：

- 签名证书的电子邮件必须与极狐GitLab 中已验证的电子邮件地址匹配。
- 极狐GitLab 实例需要从签名中的证书到极狐GitLab 证书存储中受信任证书的完整信任链。此链可能包括签名中提供的中间证书。您可能需要添加证书，例如证书颁发机构根证书，[到极狐GitLab 证书存储](https://gitlab.cn/docs/omnibus/settings/ssl/#install-custom-public-certificates)。
- 签名时间必须在[证书有效期](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5)的时间范围内，通常最长为三年。
- 签名时间等于或晚于提交时间。

> [!note]
> 如果信任链中的根 CA 或中间证书过期并续订，提交可能会暂时显示为“未验证”，直到您[重新验证它们](#re-verify-commits)。

如果提交的状态已经确定并存储在数据库中，请使用 Rake 任务[重新检查状态](../../../../administration/raketasks/x509_signatures.md)。极狐GitLab 通过后台工作进程每天检查证书吊销列表。

<a id="known-issues"></a>

## 已知问题

- 没有 `authorityKeyIdentifier`、`subjectKeyIdentifier` 和 `crlDistributionPoints` 的证书显示为 **未验证**。我们建议使用符合 [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280) 的 PKI 颁发的证书。
- **已验证** 徽章不会在 JihuLab.com 上显示，因为[上传自定义证书颁发机构 (CA)](https://gitlab.cn/docs/omnibus/settings/ssl/#install-custom-public-certificates) 仅适用于私有化部署。
- 在证书的扩展密钥用法 (EKU) 部分设置值，除了必需的 `Digital Signature` 密钥用法 (KU) 外，可能会导致您的提交显示为 **未验证**。要解决此问题，请将 `emailProtection` 添加到您的 EKU 列表中。RFC 5280 指定了此限制。要诊断它，请遵循 [使用 OpenSSL 进行 S/MIME 验证](#smime-verification-with-openssl)。

<a id="configure-for-signed-commits"></a>

## 配置签名提交

要签署您的提交、标签或两者，您必须：

1. [获取 X.509 密钥对](#obtain-an-x509-key-pair)。
1. [将您的 X.509 证书与 Git 关联](#associate-your-x509-certificate-with-git)。
1. [签署并验证提交](#sign-and-verify-commits)。
1. [签署并验证标签](#sign-and-verify-tags)。

<a id="obtain-an-x509-key-pair"></a>

### 获取 X.509 密钥对

如果您的组织有公钥基础设施 (PKI)，则该 PKI 提供 S/MIME 密钥。如果您没有来自 PKI 的 S/MIME 密钥对，请创建自己的自签名对或购买一对。

<a id="associate-your-x509-certificate-with-git"></a>

### 将您的 X.509 证书与 Git 关联

要利用 X.509 签名，您需要 Git 2.19.0 或更高版本。您可以使用命令 `git --version` 检查您的 Git 版本。

如果您有正确的版本，可以继续配置 Git。

{{< tabs >}}

{{< tab title="Linux" >}}

配置 Git 以使用您的密钥进行签名：

```shell
signingkey=$( gpgsm --list-secret-keys | egrep '(key usage|ID)' | grep -B 1 digitalSignature | awk '/ID/ {print $2}' )
git config --global user.signingkey $signingkey
git config --global gpg.format x509
```

{{< /tab >}}

{{< tab title="Windows 和 macOS" >}}

配置 Windows 或 macOS：

1. 通过以下方式安装 [S/MIME Sign](https://github.com/github/smimesign)：
   - 下载安装程序。
   - 在 macOS 上运行 `brew install smimesign`。
1. 通过运行 `smimesign --list-keys` 获取证书的 ID。
1. 通过运行 `git config --global user.signingkey <ID>` 设置您的签名密钥，将 `<ID>` 替换为证书 ID。
1. 使用以下命令配置 X.509：

   ```shell
   git config --global gpg.x509.program smimesign
   git config --global gpg.format x509
   ```

{{< /tab >}}

<a id="sign-and-verify-commits"></a>

### 签署并验证提交

在您[将您的 X.509 证书与 Git 关联](#associate-your-x509-certificate-with-git)之后，您可以签署您的提交：

1. 当您创建 Git 提交时，添加 `-S` 标志：

   ```shell
   git commit -S -m "feat: x509 signed commits"
   ```

1. 推送到极狐GitLab，并使用 `--show-signature` 标志检查您的提交是否已验证：

   ```shell
   git log --show-signature
   ```

1. *如果您不想每次提交时都输入 `-S` 标志，* 请运行此命令，让 Git 每次都对您的提交进行签名：

   ```shell
   git config --global commit.gpgsign true
   ```

<a id="sign-and-verify-tags"></a>

### 签署并验证标签

在您[将您的 X.509 证书与 Git 关联](#associate-your-x509-certificate-with-git)之后，您可以开始签署您的标签：

1. 当您创建 Git 标签时，添加 `-s` 标志：

   ```shell
   git tag -s v1.1.1 -m "My signed tag"
   ```

1. 推送到极狐GitLab，并使用以下命令验证您的标签是否已签名：

   ```shell
   git tag --verify v1.1.1
   ```

1. *如果您不想每次打标签时都输入 `-s` 标志，* 请运行此命令，让 Git 每次都对您的标签进行签名：

   ```shell
   git config --global tag.gpgsign true
   ```

## 故障排除

对于没有管理员访问权限的提交者，请查看[签名提交的验证问题](_index.md#fix-verification-problems-with-signed-commits)列表以获取可能的修复方法。本页上的其他故障排除建议需要管理员访问权限。

<a id="re-verify-commits"></a>

### 重新验证提交

极狐GitLab 将已检查提交的状态存储在数据库中。您可以在以下情况后重新验证提交：

- 续订根 CA 或中间证书。
- 对证书存储进行更改。

要重新验证提交：

1. 确保根 CA 和任何中间证书都在极狐GitLab 证书存储中。
1. 运行 [`update_signatures` Rake 任务](../../../../administration/raketasks/x509_signatures.md)以检查并更新先前已验证提交的状态。

<a id="main-verification-checks"></a>

### 主要验证检查

代码执行[这些关键检查](https://jihulab.com/gitlab-cn/gitlab/-/blob/v14.1.0-ee/lib/gitlab/x509/signature.rb#L33)，所有这些检查都必须返回 `verified`：

- `x509_certificate.nil?` 应为 false。
- `x509_certificate.revoked?` 应为 false。
- `verified_signature` 应为 true。
- `user.nil?` 应为 false。
- `user.verified_emails.include?(@email)` 应为 true。
- `certificate_email == @email` 应为 true。

要调查提交显示为 `Unverified` 的原因：

1. [启动 Rails 控制台](../../../../administration/operations/rails_console.md#starting-a-rails-console-session)：

   ```shell
   sudo gitlab-rails console
   ```

1. 确定您要调查的项目（通过路径或 ID）和完整的提交 SHA。使用此信息创建 `signature` 以运行其他检查：

   ```ruby
   project = Project.find_by_full_path('group/subgroup/project')
   project = Project.find_by_id('121')
   commit = project.repository.commit_by(oid: '87fdbd0f9382781442053b0b76da729344e37653')
   signedcommit=Gitlab::X509::Commit.new(commit)
   signature=Gitlab::X509::Signature.new(signedcommit.signature_text, signedcommit.signed_text, commit.committer_email, commit.created_at, commit.project)
   ```

   如果您进行了更改以解决运行检查时发现的问题，请重新启动 Rails 控制台并从头再次运行检查。

1. 检查提交上的证书：

   ```ruby
   signature.x509_certificate.nil?
   signature.x509_certificate.revoked?
   ```

   两项检查都应返回 `false`：

   ```ruby
   > signature.x509_certificate.nil?
   => false
   > signature.x509_certificate.revoked?
   => false
   ```

1. 对签名运行加密检查。代码必须返回 `true`：

   ```ruby
   signature.verified_signature
   ```

   如果返回 `false`，则[进一步调查此检查](#cryptographic-verification-checks)。

1. 确认提交和签名上的电子邮件地址匹配：

   - Rails 控制台会显示正在比较的电子邮件地址。
   - 最终命令必须返回 `true`：

   ```ruby
   sigemail=signature.__send__:certificate_email
   commitemail=commit.committer_email
   sigemail == commitemail
   ```

   在极狐GitLab 16.2 及更早版本中，仅比较 `Subject Alternative Name` 列表中的第一个电子邮件。要显示 `Subject Alternative Name` 列表，请运行：

   ```ruby
   signature.__send__ :get_certificate_extension,'subjectAltName'
   ```

   如果开发者的电子邮件地址不是列表中的第一个，则此检查失败，并且提交被标记为 `unverified`。

1. 提交上的电子邮件地址必须与极狐GitLab 中的账户关联。此检查应返回 `false`：

   ```ruby
   signature.user.nil?
   ```

1. 检查电子邮件地址是否与极狐GitLab 中的用户关联。此检查应返回一个用户，例如 `#<User id:1234 @user_handle>`：

   ```ruby
   User.find_by_any_email(commit.committer_email)
   ```

   如果返回 `nil`，则电子邮件地址未与用户关联，检查失败。

1. 确认开发者的电子邮件地址已验证。此检查必须返回 true：

   ```ruby
   signature.user.verified_emails.include?(commit.committer_email)
   ```

   如果前一项检查返回 `nil`，则此命令会显示错误：

   ```plaintext
   NoMethodError (undefined method `verified_emails' for nil:NilClass)
   ```

1. 验证状态存储在数据库中。要显示数据库记录：

   ```ruby
   pp CommitSignatures::X509CommitSignature.by_commit_sha(commit.sha);nil
   ```

   如果所有先前的检查都返回了正确的值：

   - `verification_status: "unverified"` 表示数据库记录需要更新。[使用 Rake 任务](#re-verify-commits)。

   - `[]` 表示数据库尚无记录。在极狐GitLab 中找到该提交以检查签名并存储结果。

<a id="cryptographic-verification-checks"></a>

#### 加密验证检查

如果极狐GitLab 确定 `verified_signature` 为 `false`，请在 Rails 控制台中调查原因。这些检查需要 `signature` 存在。请参阅先前[主要验证检查](#main-verification-checks)中的 `signature` 步骤。

1. 在不检查颁发者的情况下检查签名，应返回 `true`：

   ```ruby
   signature.__send__ :valid_signature?
   ```

1. 检查签名时间和日期。此检查必须返回 `true`：

   ```ruby
   signature.__send__ :valid_signing_time?
   ```

   - 代码允许代码签名证书过期。
   - 提交必须在证书的有效期内签名，并且等于或晚于提交的日期戳。使用以下命令显示提交时间和证书详细信息，包括 `not_before`、`not_after`：

     ```ruby
     commit.created_at
     pp signature.__send__ :cert; nil
     ```

1. 检查签名，包括是否可以建立 TLS 信任。此检查必须返回 `true`：

   ```ruby
   signature.__send__(:p7).verify([], signature.__send__(:cert_store), signature.__send__(:signed_text))
   ```

   1. 如果失败，请将建立信任所需的缺失证书添加到[极狐GitLab 证书存储](https://gitlab.cn/docs/omnibus/settings/ssl/#install-custom-public-certificates)。

   1. 添加更多证书后，（如果这些故障排除步骤随后通过）运行 Rake 任务以[重新验证提交](#re-verify-commits)。

   1. 您可以在 Rails 控制台中动态添加其他证书，以检查这是否能解决问题。

      1. 使用可修改的信任存储 `cert_store` 重新测试签名。它应该仍然失败，返回 `false`：

         ```ruby
         cert_store = signature.__send__ :cert_store
         signature.__send__(:p7).verify([], cert_store, signature.__send__(:signed_text))
         ```

      1. 添加一个额外的证书，然后重新测试：

         ```ruby
         cert_store.add_file("/etc/ssl/certs/my_new_root_ca.pem")
         signature.__send__(:p7).verify([], cert_store, signature.__send__(:signed_text))
         ```

   1. 显示签名中包含的证书：

      ```ruby
      pp signature.__send__(:p7).certificates ; nil
      ```

   1. [可以使用命令行上的 OpenSSL 进行进一步调查](#smime-verification-with-openssl)。

确保将任何额外的中间证书和根证书添加到证书存储中。为了与 Web 服务器上构建证书链的方式保持一致：

- 签署提交的 Git 客户端应在签名中包含证书和所有中间证书。
- 极狐GitLab 证书存储应仅包含根证书。

如果您从极狐GitLab 信任存储中删除根证书（例如，当它过期时），链回该根的提交签名将显示为 `unverified`。

<a id="smime-verification-with-openssl"></a>

#### 使用 OpenSSL 进行 S/MIME 验证

如果签名存在问题，或者 TLS 信任失败，可以在命令行上使用 OpenSSL 进行进一步调试。

从 [Rails 控制台](../../../../administration/operations/rails_console.md#starting-a-rails-console-session)导出签名和签名文本：

1. 需要[主要验证检查](#main-verification-checks)中的前两个步骤，以便设置 `signature`。
1. OpenSSL 要求 PKCS7 PEM 格式的数据以 `BEGIN PKCS7` 和 `END PKCS7` 为边界，因此通常需要修复此问题：

   ```ruby
   pkcs7_text = signature.signature_text.sub('-----BEGIN SIGNED MESSAGE-----', '-----BEGIN PKCS7-----')
   pkcs7_text = pkcs7_text.sub('-----END SIGNED MESSAGE-----', '-----END PKCS7-----')
   ```

1. 写出签名和签名文本：

   ```ruby
   f1=File.new('/tmp/signature_text.pk7.pem','w')
   f1 << pkcs7_text
   f1.close

   f2=File.new('/tmp/signed_text.txt','w')
   f2 << signature.signed_text
   f2.close
   ```

现在可以在 Linux 命令行上使用 OpenSSL 调查这些数据：

1. 可以查询包含签名的 PKCS #7 文件：

   ```shell
   /opt/gitlab/embedded/bin/openssl pkcs7 -inform pem -print_certs \
       -in /tmp/signature_text.pk7.pem -print -noout
   ```

   输出中应至少包含一个 `cert` 部分；即签名者的证书。

   输出中有很多低级细节。以下是一些应存在的结构和标题示例：

   ```plaintext
   PKCS7:
     d.sign:
       cert:
           cert_info:
             issuer:
             validity:
               notBefore:
               notAfter:
             subject:
   ```

   如果开发者的代码签名证书是由中间证书颁发机构颁发的，则应有额外的证书详细信息：

   ```plaintext
   PKCS7:
     d.sign:
       cert:
           cert_info:
       cert:
           cert_info:
   ```

1. 从签名中提取证书：

   ```shell
   /opt/gitlab/embedded/bin/openssl pkcs7 -inform pem -print_certs \
       -in /tmp/signature_text.pk7.pem -out /tmp/signature_cert.pem
   ```

   如果此步骤失败，则签名可能缺少签名者的证书。

   - 在 Git 客户端上修复此问题。
   - 以下步骤将失败，但如果您将签名者的证书复制到极狐GitLab 服务器，则可以使用 `-nointern -certfile signerscertificate.pem` 进行一些测试。

1. 使用提取的证书部分验证提交：

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt \
       -noverify -certfile /tmp/signature_cert.pem -nointern
   ```

   输出通常包括：

   - 父提交
   - 提交中的姓名、电子邮件和时间戳
   - 提交文本
   - `Verification successful`（或类似信息）

   此检查与极狐GitLab 执行的检查不同，因为：

   - 它不验证签名者的证书 (`-noverify`)
   - 验证是使用提供的 `-certfile` 而不是消息中的证书 (`-nointern`) 完成的

1. 使用消息中的证书部分验证提交：

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt \
       -noverify
   ```

   这应该与上一步使用提取的证书得到相同的结果。

   如果消息缺少证书，则错误包括 `signer certificate not found`。

1. 完全验证提交：

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt
   ```

   如果此步骤失败，则在极狐GitLab 中验证也会失败。

   解决任何错误，例如：

   - `certificate verify error .. unable to get local issuer certificate`：
     - 无法建立信任链。
     - 此 OpenSSL 二进制文件使用极狐GitLab 信任存储。要么信任存储中缺少根证书，要么签名中缺少中间证书，无法构建到受信任根的链。
       - 如果无法将中间证书包含在签名中，可以将其放入信任存储中。
       - [为打包的极狐GitLab 添加证书到信任存储的过程](https://gitlab.cn/docs/omnibus/settings/ssl/#install-custom-public-certificates) - 使用 `/etc/gitlab/trusted-certs`。
     - 使用 OpenSSL 测试其他受信任的证书：`-CAfile /path/to/rootcertificate.pem`
   - `unsupported certificate purpose`：
     - 证书必须在签名者证书的 `X509v3 Key Usage` 部分中指定 `Digital Signature`。
     - 如果指定了 `X509v3 Extended Key Usage` (EKU) 部分，则必须包含 `emailProtection`。
       有关更多详细信息，请参阅 [RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280#page-44)：

       > 如果不存在与两个（密钥用法）扩展都一致的目的，则不得将该证书用于任何目的。

   - `signer certificate not found`，可能是：
     - 您添加了 `-nointern` 参数，但未提供 `-certfile`。
     - 签名中缺少签名者的证书。
