本文档描述了将主极狐GitLab 数据库复制到从站点数据库所需的最少步骤。您可能需要根据数据库的设置和大小等属性更改某些值。

> [!note]
> 如果您的极狐GitLab 安装使用外部 PostgreSQL 实例（不由 Linux 软件包安装管理），则这些角色无法执行所有必要的配置步骤。在这种情况下，请改用 [Geo 与外部 PostgreSQL 实例](external_database.md) 流程。

确保从站点运行与主站点相同版本的极狐GitLab 企业版。确认您已为主站点添加了 [专业版或旗舰版订阅](https://gitlab.cn/pricing) 的许可证。

在测试或生产环境中执行这些步骤之前，请务必阅读并审阅所有步骤。

> [!note]
> 设置过程的各个阶段必须按文档顺序完成。
> 如果没有，请先[完成所有先前阶段](_index.md#using-linux-package-installations)再继续。

<a id="database-password-consistency-requirements"></a>

## 数据库密码一致性要求

每种与数据库相关的密码类型在所有 Geo 站点（主站点和从站点）中必须具有匹配的值。这包括：

- `postgresql['sql_replication_password']`（复制用户密码，MD5）
- `postgresql['sql_user_password']`（极狐GitLab 数据库用户密码，MD5）
- `gitlab_rails['db_password']`（极狐GitLab 数据库用户密码，明文）
- `patroni['replication_password']`（适用于 Patroni 设置，明文）
- `patroni['password']`（适用于 Patroni API 认证，明文）
- `postgresql['pgbouncer_user_password']`（使用 PgBouncer 时，MD5）

例如，主站点上配置的 `patroni['password']` 值必须与所有从站点上的 `patroni['password']` 值相同。

这些密码用于主站点和从站点之间的数据库认证和复制。使用不同的密码会导致复制失败，并阻止 Geo 正常运行。

<a id="single-instance-database-replication"></a>

## 单实例数据库复制

单实例数据库复制更易于设置，并且仍提供与集群替代方案相同的 Geo 功能。它适用于在单台机器上运行的设置，或尝试为未来集群安装评估 Geo 的场景。

单实例可以使用 Patroni 扩展为集群版本，这对于高可用性架构是推荐的。

请按照以下说明将 PostgreSQL 复制设置为单实例数据库。或者，您可以查看[多节点数据库复制](#multi-node-database-replication)说明，了解如何使用 Patroni 集群设置复制。

<a id="postgresql-replication"></a>

### PostgreSQL 复制

执行写操作的极狐GitLab 主站点连接到主数据库服务器。从站点连接到它们自己的数据库服务器（只读）。

您应该使用 [PostgreSQL 的复制槽](https://medium.com/@tk512/replication-slots-in-postgresql-b4b03d277c75) 来确保主站点保留从站点恢复所需的所有数据。详见下文。

以下指南假设：

- 您使用的是 Linux 软件包（因此使用 PostgreSQL 12 或更高版本），其中包含 [`pg_basebackup` 工具](https://www.postgresql.org/docs/16/app-pgbasebackup.html)。
- 您已经设置了一个主站点（您要从中复制的极狐GitLab 服务器），运行由您的 Linux 软件包安装管理的 PostgreSQL（或等效版本），并且您已经设置了一个新的从站点，在所有站点上使用相同的 [PostgreSQL 版本](../_index.md#requirements-for-running-geo)、操作系统和极狐GitLab。

> [!warning]
> Geo 使用流复制。不支持逻辑复制，但 [史诗 18022](https://gitlab.com/groups/gitlab-org/-/work_items/18022) 提议更改此行为。

<a id="step-1-configure-the-primary-site"></a>

#### 步骤 1. 配置主站点

1. SSH 登录到您的极狐GitLab 主站点并以 root 身份登录：

   ```shell
   sudo -i
   ```

1. [选择退出自动 PostgreSQL 升级](https://gitlab.cn/docs/omnibus/settings/database/#opt-out-of-automatic-postgresql-upgrades) 以避免升级极狐GitLab 时出现意外停机。请注意已知的 [使用 Geo 升级 PostgreSQL 时的注意事项](https://gitlab.cn/docs/omnibus/settings/database/#caveats-when-upgrading-postgresql-with-geo)。特别是对于较大的环境，必须谨慎规划和执行 PostgreSQL 升级。因此，今后请确保 PostgreSQL 升级是常规维护活动的一部分。
1. 编辑 `/etc/gitlab/gitlab.rb` 并为您的站点添加一个**唯一**名称：

   ```ruby
   ##
   ## The unique identifier for the Geo site. See
   ## https://docs.gitlab.com/administration/geo_sites/#common-settings
   ##
   gitlab_rails['geo_node_name'] = '<site_name_here>'
   ```

1. 重新配置主站点以使更改生效：

   ```shell
   gitlab-ctl reconfigure
   ```

1. 执行以下命令将站点定义为主站点：

   ```shell
   gitlab-ctl set-geo-primary-node
   ```

   此命令使用您在 `/etc/gitlab/gitlab.rb` 中定义的 `external_url`。

1. 为 `gitlab` 数据库用户定义密码：

   生成所需密码的 MD5 哈希：

   ```shell
   gitlab-ctl pg-password-md5 gitlab
   # Enter password: <your_db_password_here>
   # Confirm password: <your_db_password_here>
   # fca0b89a972d69f00eb3ec98a5838484
   ```

   编辑 `/etc/gitlab/gitlab.rb`：

   ```ruby
   # Fill with the hash generated by `gitlab-ctl pg-password-md5 gitlab`
   postgresql['sql_user_password'] = '<md5_hash_of_your_db_password>'

   # Every node that runs Puma or Sidekiq needs to have the database
   # password specified as below. If you have a high-availability setup, this
   # must be present in all application nodes.
   gitlab_rails['db_password'] = '<your_db_password_here>'
   ```

1. 为数据库[复制用户](https://www.postgresql.org/docs/16/warm-standby.html#STREAMING-REPLICATION)定义密码。

   使用在 `/etc/gitlab/gitlab.rb` 中 `postgresql['sql_replication_user']` 设置下定义的用户名。默认值为 `gitlab_replicator`。如果您将用户名更改为其他名称，请调整以下说明。

   生成所需密码的 MD5 哈希：

   ```shell
   gitlab-ctl pg-password-md5 gitlab_replicator
   # Enter password: <your_replication_password_here>
   # Confirm password: <your_replication_password_here>
   # 950233c0dfc2f39c64cf30457c3b7f1e
   ```

   编辑 `/etc/gitlab/gitlab.rb`：

   ```ruby
   # Fill with the hash generated by `gitlab-ctl pg-password-md5 gitlab_replicator`
   postgresql['sql_replication_password'] = '<md5_hash_of_your_replication_password>'
   ```

   如果您使用的是不由 Linux 软件包安装管理的外部数据库，则需要手动创建 `gitlab_replicator` 用户并为其定义密码：

   ```sql
   --- Create a new user 'replicator'
   CREATE USER gitlab_replicator;

   --- Set/change a password and grants replication privilege
   ALTER USER gitlab_replicator WITH REPLICATION ENCRYPTED PASSWORD '<replication_password>';
   ```

1. 编辑 `/etc/gitlab/gitlab.rb` 并将角色设置为 `geo_primary_role`（更多信息，请参阅 [Geo 角色](https://gitlab.cn/docs/omnibus/roles/#gitlab-geo-roles)）：

   ```ruby
   ## Geo Primary role
   roles(['geo_primary_role'])
   ```

1. 配置 PostgreSQL 以监听网络接口：

   出于安全原因，PostgreSQL 默认不监听任何网络接口。但是，Geo 要求从站点能够连接到主站点的数据库。因此，您需要每个站点的 IP 地址。

   > [!note]
   > 对于外部 PostgreSQL 实例，请参阅[其他说明](external_database.md)。

   如果您使用云提供商，可以通过云提供商的管理控制台查找每个 Geo 站点的地址。

   要查找 Geo 站点的地址，请 SSH 登录到该 Geo 站点并执行：

   ```shell
   ##
   ## Private address
   ##
   ip route get 255.255.255.255 | awk '{for (i=1; i<=NF; i++) if ($i == "src") { print "Private address:", $(i+1); exit }}'

   ##
   ## Public address
   ##
   echo "External address: $(curl --silent "ipinfo.io/ip")"
   ```

   在大多数情况下，以下地址用于配置极狐GitLab Geo：

   | 配置                           | 地址                                                               |
   |:----------------------------------------|:----------------------------------------------------------------------|
   | `postgresql['listen_address']`          | 主站点的公共或 VPC 私有地址。                     |
   | `postgresql['md5_auth_cidr_addresses']` | 主站点和从站点的公共或 VPC 私有地址。 |

   如果您使用 Google Cloud Platform、SoftLayer 或任何其他提供虚拟私有云 (VPC) 的供应商，我们建议对 `postgresql['md5_auth_cidr_addresses']` 和 `postgresql['listen_address']` 使用主站点和从站点的“私有”或“内部”地址。

   `listen_address` 选项使 PostgreSQL 对与给定地址对应的接口开放网络连接。有关更多详细信息，请参阅 [PostgreSQL 文档](https://www.postgresql.org/docs/16/runtime-config-connection.html)。

   > [!note]
   > 如果您需要使用 `0.0.0.0` 或 `*` 作为 `listen_address`，则还必须将 `127.0.0.1/32` 添加到 `postgresql['md5_auth_cidr_addresses']` 设置中，以允许 Rails 通过 `127.0.0.1` 连接。有关更多信息，请参阅 [议题 5258](https://gitlab.com/gitlab-org/omnibus-gitlab/-/issues/5258)。

   根据您的网络配置，建议的地址可能不正确。如果您的主站点和从站点通过局域网或连接可用区的虚拟网络（如 [Amazon VPC](https://aws.amazon.com/vpc/) 或 [Google VPC](https://cloud.google.com/vpc/)）连接，则应对 `postgresql['md5_auth_cidr_addresses']` 使用从站点的私有地址。

   编辑 `/etc/gitlab/gitlab.rb` 并添加以下内容，将 IP 地址替换为适合您网络配置的地址：

   ```ruby
   ##
   ## Primary address
   ## - replace '<primary_node_ip>' with the public or VPC address of your Geo primary node
   ##
   postgresql['listen_address'] = '<primary_site_ip>'

   ##
   # Allow PostgreSQL client authentication from the primary and secondary IPs. These IPs may be
   # public or VPC addresses in CIDR format, for example ['198.51.100.1/32', '198.51.100.2/32']
   ##
   postgresql['md5_auth_cidr_addresses'] = ['<primary_site_ip>/32', '<secondary_site_ip>/32']

   ##
   ## Replication settings
   ##
   # postgresql['max_replication_slots'] = 1 # Set this to be the number of Geo secondary nodes if you have more than one
   # postgresql['max_wal_senders'] = 10
   # postgresql['wal_keep_segments'] = 10
   ```

1. 暂时禁用自动数据库迁移，直到 PostgreSQL 重启并监听私有地址。编辑 `/etc/gitlab/gitlab.rb` 并将配置更改为 false：

   ```ruby
   ## Disable automatic database migrations
   gitlab_rails['auto_migrate'] = false
   ```

1. 可选。如果您想添加另一个从站点，相关设置如下所示：

   ```ruby
   postgresql['md5_auth_cidr_addresses'] = ['<primary_site_ip>/32', '<secondary_site_ip>/32', '<another_secondary_site_ip>/32']
   ```

   您可能还想编辑 `wal_keep_segments` 和 `max_wal_senders` 以匹配您的数据库复制要求。有关更多信息，请参阅 [PostgreSQL - 复制文档](https://www.postgresql.org/docs/16/runtime-config-replication.html)。

1. 保存文件并重新配置极狐GitLab，以应用数据库监听更改和复制槽更改：

   ```shell
   gitlab-ctl reconfigure
   ```

   重启 PostgreSQL 以使更改生效：

   ```shell
   gitlab-ctl restart postgresql
   ```

1. 现在 PostgreSQL 已重启并监听私有地址，请重新启用迁移。

   编辑 `/etc/gitlab/gitlab.rb` 并将配置**更改**为 `true`：

   ```ruby
   gitlab_rails['auto_migrate'] = true
   ```

   保存文件并重新配置极狐GitLab：

   ```shell
   gitlab-ctl reconfigure
   ```

1. 现在 PostgreSQL 服务器已设置为接受远程连接，请运行 `netstat -plnt | grep 5432` 以确保 PostgreSQL 正在监听主站点私有地址上的端口 `5432`。
1. 重新配置极狐GitLab 时自动生成了证书。此证书自动用于保护您的 PostgreSQL 流量免受窃听。为防止主动（“中间人”）攻击，从站点需要一份签署证书的 CA 副本。对于此自签名证书，请通过运行以下命令在主站点上复制 PostgreSQL 的 `server.crt` 文件：

   ```shell
   cat ~gitlab-psql/data/server.crt
   ```

   将输出复制到剪贴板或本地文件中。设置从站点时需要它！该证书不是敏感数据。

   但是，此证书是使用通用 `PostgreSQL` 通用名称创建的。因此，在复制数据库时必须使用 `verify-ca` 模式，否则主机名不匹配会导致错误。

1. 可选。生成您自己的 SSL 证书并手动[为 PostgreSQL 配置 SSL](https://gitlab.cn/docs/omnibus/settings/database/#configuring-ssl)，而不是使用生成的证书。

   您至少需要 SSL 证书和密钥。根据数据库 SSL 文档，将 `postgresql['ssl_cert_file']` 和 `postgresql['ssl_key_file']` 值设置为其完整路径。

   这允许您在复制数据库时使用 `verify-full` SSL 模式，并获得验证 CN 中完整主机名的额外好处。

   今后，您可以使用此证书（您也已在 `postgresql['ssl_cert_file']` 中设置）而不是之前自动生成的自签名证书。如果 CN 匹配，这允许您使用 `verify-full` 而不会出现复制错误。

   在主数据库上，打开 `/etc/gitlab/gitlab.rb` 并搜索 `postgresql['ssl_ca_file']`（CA 证书）。将其值复制到剪贴板，稍后粘贴到 `server.crt` 中。

<a id="step-2-configure-the-secondary-server"></a>

#### 步骤 2. 配置从服务器

1. SSH 登录到您的极狐GitLab 从站点并以 root 身份登录：

   ```shell
   sudo -i
   ```

1. [选择退出自动 PostgreSQL 升级](https://gitlab.cn/docs/omnibus/settings/database/#opt-out-of-automatic-postgresql-upgrades) 以避免升级极狐GitLab 时出现意外停机。请注意已知的 [使用 Geo 升级 PostgreSQL 时的注意事项](https://gitlab.cn/docs/omnibus/settings/database/#caveats-when-upgrading-postgresql-with-geo)。特别是对于较大的环境，必须谨慎规划和执行 PostgreSQL 升级。因此，今后请确保 PostgreSQL 升级是常规维护活动的一部分。
1. 停止应用服务器和 Sidekiq：

   ```shell
   gitlab-ctl stop puma
   gitlab-ctl stop sidekiq
   ```

   > [!note]
   > 此步骤很重要，以免在站点完全配置之前尝试执行任何操作。

1. [检查 TCP 连接](../../raketasks/maintenance.md) 到主站点的 PostgreSQL 服务器：

   ```shell
   gitlab-rake gitlab:tcp_check[<primary_site_ip>,5432]
   ```

   > [!note]
   > 如果此步骤失败，您可能使用了错误的 IP 地址，或者防火墙可能阻止了访问。检查 IP 地址，特别注意公共和私有地址之间的差异。确保如果存在防火墙，允许从站点连接到主站点上的端口 5432。

1. 在从站点创建一个文件 `server.crt`，内容为您在主站点设置的最后一步中获得的内容：

   ```shell
   editor server.crt
   ```

1. 在从站点上设置 PostgreSQL TLS 验证：

   为 `gitlab-psql` 用户安装 `server.crt` 文件：

   ```shell
   install \
      -D \
      -o gitlab-psql \
      -g gitlab-psql \
      -m 0400 \
      -T server.crt ~gitlab-psql/.postgresql/root.crt
   ```

   PostgreSQL 现在在验证 TLS 连接时只识别该确切证书。该证书只能由有权访问私钥的人复制，而私钥仅存在于主站点上。

   因为 `gitlab-ctl replicate-geo-database` 以 root 身份运行，请也为 root 用户安装证书。否则，当您使用 `sslmode=verify-ca` 或 `sslmode=verify-full` 时，复制命令会失败并显示 `could not open certificate file` 错误：

   ```shell
   install \
      -D \
      -o root \
      -g root \
      -m 0400 \
      -T server.crt /root/.postgresql/root.crt
   ```

1. 测试 `gitlab-psql` 用户是否可以连接到主站点的数据库（在 Linux 软件包安装中，默认数据库名称为 `gitlabhq_production`）：

   ```shell
   sudo \
      -u gitlab-psql /opt/gitlab/embedded/bin/psql \
      --list \
      -U gitlab_replicator \
      -d "dbname=gitlabhq_production sslmode=verify-ca" \
      -W \
      -h <primary_site_ip>
   ```

   > [!note]
   > 如果您使用手动生成的证书并希望使用 `sslmode=verify-full` 来利用完整主机名验证，请在运行命令时将 `verify-ca` 替换为 `verify-full`。

   出现提示时，输入您在第一步中为 `gitlab_replicator` 用户设置的明文密码。如果一切正常，您应该会看到主站点的数据库列表。

   此处连接失败表示 TLS 配置不正确。确保主站点上 `~gitlab-psql/data/server.crt` 的内容与从站点上 `~gitlab-psql/.postgresql/root.crt` 的内容匹配。

1. 编辑 `/etc/gitlab/gitlab.rb` 并将角色设置为 `geo_secondary_role`（更多信息，请参阅 [Geo 角色](https://gitlab.cn/docs/omnibus/roles/#gitlab-geo-roles)）：

   ```ruby
   ##
   ## Geo Secondary role
   ## - configure dependent flags automatically to enable Geo
   ##
   roles(['geo_secondary_role'])
   ```

1. 配置 PostgreSQL：

   此步骤类似于您配置主实例的方式。即使使用单节点，也必须启用此功能。

   > [!warning]
   > 每种密码类型必须在所有 Geo 站点中具有[匹配的值](#database-password-consistency-requirements)。

   编辑 `/etc/gitlab/gitlab.rb` 并添加以下内容，将 IP 地址替换为适合您网络配置的地址：

   ```ruby
   ##
   ## Secondary address
   ## - replace '<secondary_site_ip>' with the public or VPC address of your Geo secondary site
   ##
   postgresql['listen_address'] = '<secondary_site_ip>'
   postgresql['md5_auth_cidr_addresses'] = ['<secondary_site_ip>/32']

   ##
   ## Database credentials password (defined previously in primary site)
   ## - replicate same values here as defined in primary site
   ##
   postgresql['sql_replication_password'] = '<md5_hash_of_your_replication_password>'
   postgresql['sql_user_password'] = '<md5_hash_of_your_db_password>'
   gitlab_rails['db_password'] = '<your_db_password_here>'
   ```

   对于外部 PostgreSQL 实例，请参阅[其他说明](external_database.md)。如果您将以前的主站点重新联机作为从站点，则还必须删除 `roles(['geo_primary_role'])` 或 `geo_primary_role['enable'] = true`。

1. 重新配置极狐GitLab 以使更改生效：

   ```shell
   gitlab-ctl reconfigure
   ```

1. 重启 PostgreSQL 以使 IP 更改生效：

   ```shell
   gitlab-ctl restart postgresql
   ```

<a id="step-3-initiate-the-replication-process"></a>

#### 步骤 3. 启动复制过程

以下是一个脚本，用于将从站点上的数据库连接到主站点上的数据库。此脚本复制数据库并为流复制创建所需文件。

使用的目录是 Linux 软件包安装中设置的默认目录。如果您更改了任何默认值，请相应地配置脚本（替换任何目录和路径）。

> [!warning]
> 确保在从站点上运行此命令，因为它会在运行 `pg_basebackup` 之前删除所有 PostgreSQL 数据。

1. SSH 登录到您的极狐GitLab 从站点并以 root 身份登录：

   ```shell
   sudo -i
   ```

1. 选择一个[数据库友好名称](https://www.postgresql.org/docs/16/warm-standby.html#STREAMING-REPLICATION-SLOTS-MANIPULATION) 用作从站点的复制槽名称。例如，如果您的域名是 `secondary.geo.example.com`，请使用 `secondary_example` 作为槽名称，如下面的命令所示。

1. 执行以下命令以启动备份/恢复并开始复制

   > [!warning]
   > 每个 Geo 从站点必须具有自己唯一的复制槽名称。在两个从站点之间使用相同的槽名称会破坏 PostgreSQL 复制。

   复制槽名称只能包含小写字母、数字和下划线字符。

   出现提示时，输入您在第一步中为 `gitlab_replicator` 用户设置的明文密码。

   ```shell
   gitlab-ctl replicate-geo-database \
      --slot-name=<secondary_site_name> \
      --host=<primary_site_ip> \
      --sslmode=verify-ca
   ```

   > [!note]
   > 如果您生成了自定义 PostgreSQL 证书，则需要使用 `--sslmode=verify-full`（或完全省略 `sslmode` 行），以利用证书 CN / SAN 中完整主机名的额外验证来增强安全性。
   > 否则，使用自动创建的证书和 `verify-full` 会失败，因为它的通用 `PostgreSQL` CN 与此命令中的 `--host` 值不匹配。

   此命令还接受许多其他选项。您可以使用 `--help` 列出所有选项，但这里有一些提示：

   - 如果您的主站点是单节点，请使用主节点主机作为 `--host` 参数。
   - 如果您的主站点使用外部 PostgreSQL 数据库，则需要调整 `--host` 参数：
     - 对于 PgBouncer 设置，直接指向实际的 PostgreSQL 数据库主机，而不是 PgBouncer 地址。
     - 对于 Patroni 配置，指向当前的 Patroni 主节点主机。
     - 使用负载均衡器（例如 HAProxy）时，如果负载均衡器配置为始终路由到 Patroni 主节点，则可以指向负载均衡器的地址。如果不是，则必须指向实际的数据库主机。
     - 对于具有专用 PostgreSQL 节点的设置，直接指向专用数据库主机。
   - 将 `--slot-name` 更改为主数据库上要使用的复制槽名称。如果复制槽不存在，脚本会尝试自动创建。
   - 如果 PostgreSQL 监听非标准端口，请添加 `--port=`。
   - 如果您的数据库太大而无法在 30 分钟内传输，则需要增加超时时间。例如，如果您预计初始复制需要不到一小时，请使用 `--backup-timeout=3600`。
   - 传递 `--sslmode=disable` 以完全跳过 PostgreSQL TLS 认证（例如，您知道网络路径是安全的，或者您正在使用站点到站点 VPN）。在公共互联网上不安全！
   - 您可以在 [PostgreSQL 文档](https://www.postgresql.org/docs/16/libpq-ssl.html#LIBPQ-SSL-PROTECTION) 中阅读有关每个 `sslmode` 的更多详细信息。前面列出的说明经过精心编写，以确保防止被动窃听者和主动“中间人”攻击者。
   - 如果您要将旧站点重新用作 Geo 从站点，则必须在命令行中添加 `--force`。
   - 不在生产机器上时，您可以通过添加 `--skip-backup` 来禁用备份步骤（如果您确定这是您想要的）。

复制过程现已完成。

> [!note]
> 复制过程仅将数据从主站点的数据库复制到从站点的数据库。要完成从站点配置，请[在主站点上添加从站点](../replication/configuration.md#step-3-add-the-secondary-site)。

<a id="pgbouncer-support-optional"></a>

### PgBouncer 支持（可选）

[PgBouncer](https://www.pgbouncer.org/) 可以与极狐GitLab Geo 一起使用来池化 PostgreSQL 连接，即使在单实例安装中使用也可以提高性能。

如果您在支持 Geo 主站点的节点集群和支持 Geo 从站点的另外两个节点集群的高可用性配置中使用极狐GitLab，则应使用 PgBouncer。您需要两个 PgBouncer 节点：一个用于主数据库，另一个用于跟踪数据库。有关更多信息，请参阅[相关文档](../../postgresql/replication_and_failover.md)。

<a id="changing-the-replication-password"></a>

### 更改复制密码

> [!warning]
> 更改复制密码时，必须在所有 Geo 站点（主站点和所有从站点）上使用[相同的密码值](#database-password-consistency-requirements)进行更新。未能保持密码同步会破坏复制。

要在使用 Linux 软件包安装管理的 PostgreSQL 实例时更改[复制用户](https://www.postgresql.org/docs/16/warm-standby.html#STREAMING-REPLICATION)的密码：

在极狐GitLab Geo 主站点上：

1. 复制用户的默认值为 `gitlab_replicator`，但如果您在 `/etc/gitlab/gitlab.rb` 的 `postgresql['sql_replication_user']` 设置下设置了自定义复制用户，请确保针对您自己的用户调整以下说明。

   生成所需密码的 MD5 哈希：

   ```shell
   sudo gitlab-ctl pg-password-md5 gitlab_replicator
   # Enter password: <your_replication_password_here>
   # Confirm password: <your_replication_password_here>
   # 950233c0dfc2f39c64cf30457c3b7f1e
   ```

   编辑 `/etc/gitlab/gitlab.rb`：

   ```ruby
   # Fill with the hash generated by `gitlab-ctl pg-password-md5 gitlab_replicator`
   postgresql['sql_replication_password'] = '<md5_hash_of_your_replication_password>'
   ```

1. 保存文件并重新配置极狐GitLab 以更改 PostgreSQL 中复制用户的密码：

   ```shell
   sudo gitlab-ctl reconfigure
   ```

1. 重启 PostgreSQL 以使复制密码更改生效：

   ```shell
   sudo gitlab-ctl restart postgresql
   ```

在密码在任何从站点上更新之前，从站点上的 [PostgreSQL 日志](../../logs/_index.md#postgresql-logs) 会报告以下错误消息：

```console
FATAL:  could not connect to the primary server: FATAL:  password authentication failed for user "gitlab_replicator"
```

在所有极狐GitLab Geo 从站点上：

1. 从配置角度来看，第一步不是必需的，因为哈希的 `'sql_replication_password'` 不用于极狐GitLab Geo 从站点。但是，如果从站点需要提升为极狐GitLab Geo 主站点，请确保从站点配置中的 `'sql_replication_password'` 匹配。

   编辑 `/etc/gitlab/gitlab.rb`：

   ```ruby
   # Fill with the hash generated by `gitlab-ctl pg-password-md5 gitlab_replicator` on the Geo primary
   postgresql['sql_replication_password'] = '<md5_hash_of_your_replication_password>'
   ```

1. 在初始复制设置期间，`gitlab-ctl replicate-geo-database` 命令将复制用户帐户的明文密码写入两个位置：

   - `gitlab-geo.conf`：由 PostgreSQL 复制过程使用，写入 PostgreSQL 数据目录，默认位于 `/var/opt/gitlab/postgresql/data/gitlab-geo.conf`。
   - `.pgpass`：由 `gitlab-psql` 用户使用，默认位于 `/var/opt/gitlab/postgresql/.pgpass`。

   更新这两个文件中的明文密码，然后重启 PostgreSQL：

   ```shell
   sudo gitlab-ctl restart postgresql
   ```

## 多节点数据库复制

<a id="migrating-a-single-postgresql-node-to-patroni"></a>

### 将单个 PostgreSQL 节点迁移到 Patroni

在引入 Patroni 之前，Geo 不支持在从站点上进行 Linux 软件包安装的 HA 设置。

使用 Patroni，现在可以实现这种支持。要将现有 PostgreSQL 迁移到 Patroni：

1. 确保在从站点上设置了 Consul 集群（类似于在主站点上的设置方式）。
1. [配置永久复制槽](#step-1-configure-patroni-permanent-replication-slot-on-the-primary-site)。
1. [配置内部负载均衡器](#step-2-configure-the-internal-load-balancer-on-the-primary-site)。
1. [配置 PgBouncer 节点](#step-3-configure-pgbouncer-nodes-on-the-secondary-site)。
1. [配置 Standby 集群](#step-4-configure-a-standby-cluster-on-the-secondary-site) 在该单节点机器上。

您最终会得到一个单节点的 **Standby 集群**。这允许您按照前面列出的相同说明添加其他 Patroni 节点。

<a id="patroni-support"></a>

### Patroni 支持

Patroni 是 Geo 的官方复制管理解决方案。Patroni 可用于在主站点和从 Geo 站点上构建高可用性集群。在从站点上使用 Patroni 是可选的，您不必在每个 Geo 站点上使用相同数量的节点。

有关如何设置主站点 Patroni 的说明，请参阅[相关文档](../../postgresql/replication_and_failover.md#patroni)。

<a id="configuring-patroni-cluster-for-a-geo-secondary-site"></a>

#### 为 Geo 从站点配置 Patroni 集群

在 Geo 从站点中，主 PostgreSQL 数据库是主站点 PostgreSQL 数据库的只读副本。

生产就绪且安全的设置至少需要：

- 3 个 Consul 节点 _（主站点和从站点）_
- 2 个 Patroni 节点 _（主站点和从站点）_
- 1 个 PgBouncer 节点 _（主站点和从站点）_
- 1 个内部负载均衡器 _（仅主站点）_

每当选举出新的主节点时，内部负载均衡器都为连接到 Patroni 集群的主节点提供单一端点。负载均衡器是启用从站点级联复制所必需的。

请务必使用[密码凭据](../../postgresql/replication_and_failover.md#database-authorization-for-patroni)和其他数据库最佳实践。

<a id="step-1-configure-patroni-permanent-replication-slot-on-the-primary-site"></a>

##### 步骤 1. 在主站点上配置 Patroni 永久复制槽

在主数据库上设置持久复制槽，以确保数据从主数据库持续复制到从节点上的 Patroni 集群。

{{< tabs >}}

{{< tab title="Primary with Patroni cluster" >}}

要在从站点上使用 Patroni 设置数据库复制，您必须配置主站点 Patroni 集群上的永久复制槽，并确保使用密码认证。

在主站点上每个运行 Patroni 实例的节点上 **从 Patroni 主节点实例开始**：

1. SSH 登录到您的 Patroni 实例并以 root 身份登录：

   ```shell
   sudo -i
   ```

1. [选择退出自动 PostgreSQL 升级](https://gitlab.cn/docs/omnibus/settings/database/#opt-out-of-automatic-postgresql-upgrades) 以避免升级极狐GitLab 时出现意外停机。请注意已知的 [使用 Geo 升级 PostgreSQL 时的注意事项](https://gitlab.cn/docs/omnibus/settings/database/#caveats-when-upgrading-postgresql-with-geo)。特别是对于较大的环境，必须谨慎规划和执行 PostgreSQL 升级。因此，今后请确保 PostgreSQL 升级是常规维护活动的一部分。
1. 编辑 `/etc/gitlab/gitlab.rb` 并添加以下内容。确保每种密码类型在所有 Geo 站点中具有[匹配的值](#database-password-consistency-requirements)。

   ```ruby
   roles(['patroni_role'])

   consul['services'] = %w(postgresql)
   consul['configuration'] = {
     retry_join: %w[CONSUL_PRIMARY1_IP CONSUL_PRIMARY2_IP CONSUL_PRIMARY3_IP]
   }

   # You need one entry for each secondary, with a unique name following PostgreSQL slot_name constraints:
   #
   # Configuration syntax is: 'unique_slotname' => { 'type' => 'physical' },
   # We don't support setting a permanent replication slot for logical replication type
   patroni['replication_slots'] = {
     'geo_secondary' => { 'type' => 'physical' }
   }

   patroni['use_pg_rewind'] = true
   patroni['postgresql']['max_wal_senders'] = 8 # Use double of the amount of patroni/reserved slots (3 patronis + 1 reserved slot for a Geo secondary).
   patroni['postgresql']['max_replication_slots'] = 8 # Use double of the amount of patroni/reserved slots (3 patronis + 1 reserved slot for a Geo secondary).
   patroni['username'] = 'PATRONI_API_USERNAME'
   patroni['password'] = 'PATRONI_API_PASSWORD'
   patroni['replication_password'] = 'PLAIN_TEXT_POSTGRESQL_REPLICATION_PASSWORD'

   # Add all patroni nodes to the allowlist
   patroni['allowlist'] = %w[
     127.0.0.1/32
     PATRONI_PRIMARY1_IP/32 PATRONI_PRIMARY2_IP/32 PATRONI_PRIMARY3_IP/32
     PATRONI_SECONDARY1_IP/32 PATRONI_SECONDARY2_IP/32 PATRONI_SECONDARY3_IP/32
   ]

   # We list all secondary instances as they can all become a Standby Leader
   postgresql['md5_auth_cidr_addresses'] = %w[
     PATRONI_PRIMARY1_IP/32 PATRONI_PRIMARY2_IP/32 PATRONI_PRIMARY3_IP/32 PATRONI_PRIMARY_PGBOUNCER/32
     PATRONI_SECONDARY1_IP/32 PATRONI_SECONDARY2_IP/32 PATRONI_SECONDARY3_IP/32 PATRONI_SECONDARY_PGBOUNCER/32
   ]

   postgresql['pgbouncer_user_password'] = 'PGBOUNCER_PASSWORD_HASH'
   postgresql['sql_replication_password'] = 'POSTGRESQL_REPLICATION_PASSWORD_HASH'
   postgresql['sql_user_password'] = 'POSTGRESQL_PASSWORD_HASH'
   postgresql['listen_address'] = '0.0.0.0' # You can use a public or VPC address here instead
   ```

1. 重新配置极狐GitLab 以使更改生效：

   ```shell
   gitlab-ctl reconfigure
   ```

1. SSH 登录到您的单节点实例并以 root 身份登录：

[选择退出自动 PostgreSQL 升级](https://gitlab.cn/docs/omnibus/settings/database/#opt-out-of-automatic-postgresql-upgrades) 以避免升级极狐GitLab 时出现意外停机。请注意已知的 [使用 Geo 升级 PostgreSQL 时的注意事项](https://gitlab.cn/docs/omnibus/settings/database/#caveats-when-upgrading-postgresql-with-geo)。特别是对于较大的环境，必须谨慎规划和执行 PostgreSQL 升级。因此，今后请确保 PostgreSQL 升级是常规维护活动的一部分。
1. 编辑 `/etc/gitlab/gitlab.rb` 并添加以下内容：

   ```ruby

   postgresql['max_replication_slots'] = 2 # Use 2 per secondary site (1 temporary slot for initial Patroni replication + 1 reserved slot for a Geo secondary)
   ```

1. 重新配置极狐GitLab：

   ```shell
   gitlab-ctl reconfigure
   ```

1. 重启 PostgreSQL 服务以使新更改生效：


1. 启动数据库控制台

   ```shell
   gitlab-psql
   ```

1. 在主站点上配置永久复制槽

   ```sql
   select pg_create_physical_replication_slot('geo_secondary')
   ```

1. 可选。如果主站点没有 PgBouncer，但从站点有：

   在主站点上配置 `pgbouncer` 用户，并为 Linux 软件包附带的 PgBouncer 添加必要的 `pg_shadow_lookup` 函数。从服务器上的 PgBouncer 应该仍然能够连接到从站点上的 PostgreSQL 节点。

   ```sql
   --- Create a new user 'pgbouncer'
   CREATE USER pgbouncer;

   --- Set/change a password and grants replication privilege
   ALTER USER pgbouncer WITH REPLICATION ENCRYPTED PASSWORD '<pgbouncer_password_from_secondary>';

   CREATE OR REPLACE FUNCTION public.pg_shadow_lookup(in i_username text, out username text, out password text) RETURNS record AS $$
   BEGIN
       SELECT usename, passwd FROM pg_catalog.pg_shadow
       WHERE usename = i_username INTO username, password;
       RETURN;
   END;
   $$ LANGUAGE plpgsql SECURITY DEFINER;

   REVOKE ALL ON FUNCTION public.pg_shadow_lookup(text) FROM public, pgbouncer;
   GRANT EXECUTE ON FUNCTION public.pg_shadow_lookup(text) TO pgbouncer;
   ```

<a id="step-2-configure-the-internal-load-balancer-on-the-primary-site"></a>

##### 步骤 2. 在主站点上配置内部负载均衡器

为避免在主站点上选举出新主节点时重新配置从站点上的 Standby Leader，您应该设置一个 TCP 内部负载均衡器。此负载均衡器为连接到 Patroni 集群的主节点提供单一端点。

Linux 软件包不包含负载均衡器。以下是使用 [HAProxy](https://www.haproxy.org/) 的方法。

以下 IP 和名称用作示例：

- `10.6.0.21`: Patroni 1 (`patroni1.internal`)
- `10.6.0.22`: Patroni 2 (`patroni2.internal`)
- `10.6.0.23`: Patroni 3 (`patroni3.internal`)

```plaintext
global
    log /dev/log local0
    log localhost local1 notice
    log stdout format raw local0

defaults
    log global
    default-server inter 3s fall 3 rise 2 on-marked-down shutdown-sessions

frontend internal-postgresql-tcp-in
    bind *:5432
    mode tcp
    option tcplog

    default_backend postgresql

backend postgresql
    mode tcp
    option httpchk
    http-check expect status 200

    server patroni1.internal 10.6.0.21:5432 maxconn 100 check port 8008
    server patroni2.internal 10.6.0.22:5432 maxconn 100 check port 8008
    server patroni3.internal 10.6.0.23:5432 maxconn 100 check port 8008
```

有关进一步指导，请参阅您首选的负载均衡器的文档。

<a id="step-3-configure-pgbouncer-nodes-on-the-secondary-site"></a>

##### 步骤 3. 在从站点上配置 PgBouncer 节点

生产就绪且高可用性的配置至少需要三个 Consul 节点和至少一个 PgBouncer 节点。但是，建议每个数据库节点使用一个 PgBouncer 节点。当有多个 PgBouncer 服务节点时，需要内部负载均衡器 (TCP)。内部负载均衡器为连接到 PgBouncer 集群提供单一端点。有关更多信息，请参阅[相关文档](../../postgresql/replication_and_failover.md)。

在从站点上每个运行 PgBouncer 实例的节点上：

1. SSH 登录到您的 PgBouncer 节点并以 root 身份登录：

   ```shell
   sudo -i
   ```

1. 编辑 `/etc/gitlab/gitlab.rb` 并添加以下内容：

   ```ruby
   # Disable all components except Pgbouncer and Consul agent
   roles(['pgbouncer_role'])

   # PgBouncer configuration
   pgbouncer['admin_users'] = %w(pgbouncer gitlab-consul)
   pgbouncer['users'] = {
   'gitlab-consul': {
      # Generate it with: `gitlab-ctl pg-password-md5 gitlab-consul`
      password: 'GITLAB_CONSUL_PASSWORD_HASH'
    },
     'pgbouncer': {
       # Generate it with: `gitlab-ctl pg-password-md5 pgbouncer`
       password: 'PGBOUNCER_PASSWORD_HASH'
     }
   }

   # Consul configuration
   consul['watchers'] = %w(postgresql)
   consul['configuration'] = {
     retry_join: %w[CONSUL_SECONDARY1_IP CONSUL_SECONDARY2_IP CONSUL_SECONDARY3_IP]
   }
   consul['monitoring_service_discovery'] =  true
   ```

1. 重新配置极狐GitLab 以使更改生效：

   ```shell
   gitlab-ctl reconfigure
   ```

1. 创建一个 `.pgpass` 文件，以便 Consul 能够重新加载 PgBouncer。在询问时输入 `PLAIN_TEXT_PGBOUNCER_PASSWORD` 两次：

   ```shell
   gitlab-ctl write-pgpass --host 127.0.0.1 --database pgbouncer --user pgbouncer --hostuser gitlab-consul
   ```

1. 重新加载 PgBouncer 服务：

   ```shell
   gitlab-ctl hup pgbouncer
   ```

<a id="step-4-configure-a-standby-cluster-on-the-secondary-site"></a>

##### 步骤 4. 在从站点上配置 Standby 集群

> [!note]
> 如果您要将具有单个 PostgreSQL 实例的从站点转换为 Patroni 集群，则必须从该 PostgreSQL 实例开始。它成为 Patroni Standby Leader 实例，然后您可以根据需要切换到另一个副本。

对于从站点上每个运行 Patroni 实例的节点：

1. SSH 登录到您的 Patroni 节点并以 root 身份登录：

   ```shell
   sudo -i
   ```

1. [选择退出自动 PostgreSQL 升级](https://gitlab.cn/docs/omnibus/settings/database/#opt-out-of-automatic-postgresql-upgrades) 以避免升级极狐GitLab 时出现意外停机。请注意已知的 [使用 Geo 升级 PostgreSQL 时的注意事项](https://gitlab.cn/docs/omnibus/settings/database/#caveats-when-upgrading-postgresql-with-geo)。特别是对于较大的环境，必须谨慎规划和执行 PostgreSQL 升级。因此，今后请确保 PostgreSQL 升级是常规维护活动的一部分。
1. 编辑 `/etc/gitlab/gitlab.rb` 并添加以下内容：

   > [!warning]
   > 每种密码类型必须在所有 Geo 站点中具有[匹配的值](#database-password-consistency-requirements)。

   ```ruby
   roles(['consul_role', 'patroni_role'])

   consul['enable'] = true
   consul['configuration'] = {
     retry_join: %w[CONSUL_SECONDARY1_IP CONSUL_SECONDARY2_IP CONSUL_SECONDARY3_IP]
   }
   consul['services'] = %w(postgresql)

   postgresql['md5_auth_cidr_addresses'] = [
     'PATRONI_SECONDARY1_IP/32', 'PATRONI_SECONDARY2_IP/32', 'PATRONI_SECONDARY3_IP/32', 'PATRONI_SECONDARY_PGBOUNCER/32',
     # Any other instance that needs access to the database as per documentation
   ]


   # Add patroni nodes to the allowlist
   patroni['allowlist'] = %w[
     127.0.0.1/32
     PATRONI_SECONDARY1_IP/32 PATRONI_SECONDARY2_IP/32 PATRONI_SECONDARY3_IP/32
   ]

   patroni['standby_cluster']['enable'] = true
   patroni['standby_cluster']['host'] = 'INTERNAL_LOAD_BALANCER_PRIMARY_IP'
   patroni['standby_cluster']['port'] = INTERNAL_LOAD_BALANCER_PRIMARY_PORT
   patroni['standby_cluster']['primary_slot_name'] = 'geo_secondary' # Or the unique replication slot name you setup before
   patroni['username'] = 'PATRONI_API_USERNAME'
   patroni['password'] = 'PATRONI_API_PASSWORD'
   patroni['replication_password'] = 'PLAIN_TEXT_POSTGRESQL_REPLICATION_PASSWORD'
   patroni['use_pg_rewind'] = true
   patroni['postgresql']['max_wal_senders'] = 5 # A minimum of three for one replica, plus two for each additional replica
   patroni['postgresql']['max_replication_slots'] = 5 # A minimum of three for one replica, plus two for each additional replica

   postgresql['pgbouncer_user_password'] = 'PGBOUNCER_PASSWORD_HASH'
   postgresql['sql_replication_password'] = 'POSTGRESQL_REPLICATION_PASSWORD_HASH'
   postgresql['sql_user_password'] = 'POSTGRESQL_PASSWORD_HASH'
   postgresql['listen_address'] = '0.0.0.0' # You can use a public or VPC address here instead

   # GitLab Rails configuration is required for `gitlab-ctl geo-replication-pause`
   gitlab_rails['db_password'] = 'POSTGRESQL_PASSWORD'
   gitlab_rails['enable'] = true
   gitlab_rails['auto_migrate'] = false
   ```

   配置 `patroni['standby_cluster']['host']` 和 `patroni['standby_cluster']['port']` 时：
   - `INTERNAL_LOAD_BALANCER_PRIMARY_IP` 必须指向主内部负载均衡器 IP。
   - `INTERNAL_LOAD_BALANCER_PRIMARY_PORT` 必须指向[为主 Patroni 集群主节点配置的](#step-2-configure-the-internal-load-balancer-on-the-primary-site)前端端口。不要使用 PgBouncer 前端端口。

1. 重新配置极狐GitLab 以使更改生效。此步骤是引导 PostgreSQL 用户和设置所必需的。

   - 如果是全新安装 Patroni：

     ```shell
     gitlab-ctl reconfigure
     ```

   - 如果您在以前具有正常工作的 Patroni 集群的站点上配置 Patroni standby 集群：

     1. 停止所有由 Patroni 管理的节点上的 Patroni，包括级联副本：

        ```shell
        gitlab-ctl stop patroni
        ```

     1. 在主 Patroni 节点上运行以下命令以重新创建 standby 集群：

        ```shell
        rm -rf /var/opt/gitlab/postgresql/data
        /opt/gitlab/embedded/bin/patronictl -c /var/opt/gitlab/patroni/patroni.yaml remove postgresql-ha
        gitlab-ctl reconfigure
        ```

     1. 在主 Patroni 节点上启动 Patroni 以启动从主数据库的复制过程：

        ```shell
        gitlab-ctl start patroni
        ```

     1. 检查 Patroni 集群的状态：

        ```shell
        gitlab-ctl patroni members
        ```

        验证：

        - 当前 Patroni 节点出现在输出中。
        - 角色是 `Standby Leader`。角色最初可能显示为 `Replica`。
        - 状态是 `Running`。状态最初可能显示为 `Creating replica`。

        等待节点的角色稳定为 `Standby Leader` 且状态为 `Running`。这可能需要几分钟。

     1. 当主 Patroni 节点是 `Standby Leader` 且状态为 `Running` 时，启动 standby 集群中的其他 Patroni 节点：

        ```shell
        gitlab-ctl start patroni
        ```

        其他 Patroni 节点应作为副本加入新的 standby 集群，并自动开始从主 Patroni 节点复制。

1. 验证集群状态：

   ```shell
   gitlab-ctl patroni members
   ```

   确保所有 Patroni 节点都列在 `Running` 状态中。应该有一个 `Standby Leader` 节点和多个 `Replica` 节点。

<a id="migrating-a-single-tracking-database-node-to-patroni"></a>

### 将单个跟踪数据库节点迁移到 Patroni

在引入 Patroni 之前，Geo 不支持在从站点上进行 Linux 软件包安装的 HA 设置。

使用 Patroni，现在可以支持 HA 设置。但是，Patroni 中的某些限制阻止在同一台机器上管理两个不同的集群。您应该按照描述如何[为 Geo 从站点配置 Patroni 集群](#configuring-patroni-cluster-for-a-geo-secondary-site)的相同说明，为跟踪数据库设置一个新的 Patroni 集群。

从节点会回填新的跟踪数据库，无需数据同步。

<a id="configuring-patroni-cluster-for-the-tracking-postgresql-database"></a>

### 为跟踪 PostgreSQL 数据库配置 Patroni 集群

从 Geo 站点使用单独的 PostgreSQL 安装作为跟踪数据库，以跟踪复制状态并自动从潜在的复制问题中恢复。

如果您想在单节点上运行 Geo 跟踪数据库，请参阅[在 Geo 从站点上配置 Geo 跟踪数据库](../replication/multiple_servers.md#step-2-configure-the-geo-tracking-database-on-the-geo-secondary-site)。

Linux 软件包不支持在高可用性配置中运行 Geo 跟踪数据库。特别是，故障转移无法正常工作。请参阅[功能请求议题](https://gitlab.com/gitlab-org/omnibus-gitlab/-/issues/7292)。

如果您想在高可用性配置中运行 Geo 跟踪数据库，您可以将从站点连接到外部 PostgreSQL 数据库，例如云管理数据库，或手动配置的 [Patroni](https://patroni.readthedocs.io/en/latest/) 集群（不由极狐GitLab Linux 软件包管理）。请遵循 [Geo 与外部 PostgreSQL 实例](external_database.md#configure-the-tracking-database)。
